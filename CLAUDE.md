# CLAUDE.md

> Last reviewed: 2026-09-06

Приложение Битрикс24 с ТРЕМЯ отчётами по CRM. Встраивается в раздел CRM-аналитики портала: там
ПУНКТ МЕНЮ НА КАЖДЫЙ отчёт. Главная приложения (`/app`, плитка в «Приложениях») — выбор
отчёта. Данные CRM только читаются; в портал пишется ДВА своих значения, оба в `user.option`:
выбранный отбор и одноразовое условие открываемой детализации.

| Отчёт | Адрес | О чём |
|---|---|---|
| **Аналитика по лидам** | `/app/leads` | путь лида от поступления до закрытия сделки: воронка, брак с причинами, причины проигрыша, источники |
| **Сделки по менеджерам** | `/app/managers` | сколько сделок у каждого менеджера в каждой «моей компании» и на какой стадии: кольцевая диаграмма и таблицы |
| **Активность пользователей** | `/app/activity` | сколько каждый сотрудник за период звонил, сколько наговорил и сколько сделал дел в CRM: разговоры по направлениям с длительностью, недозвоны, письма, встречи, задачи, лиды |

> **Статус:** выкачено, встроено в портал и считает ЖИВЫЕ данные. Отчёт 1 — лиды счётчиками,
> сделки из лидов строками (месяц ≈ 17 с на боевом портале заказчика); фоном после основного
> отчёта — успешные сделки без лида (≈ минута) и история стадий для времени первого ответа (≈ две).
> Отчёт 2 — только счётчики, ≈ 6 с на направление за месяц (компания в отчёте одна, выбирается
> фильтром).
> Отчёт 3 — дела и лиды счётчиками (≈ 6 с), звонки СТРОКАМИ и фоном (≈ 1,5 мин на месяц):
> длительности разговора нет ни в одном агрегате портала.
> Вне портала (`?preview=1`) — демо-набор, и экран говорит об этом прямо.

> ⚠ **Главное про этот проект:** спорным местом здесь оказались не технологии, а АРИФМЕТИКА.
> ТЗ и согласованный макет считают конверсии по разным знаменателям и дают на одних данных
> 100 % против 80 %. Прежде чем править любую формулу — [`docs/METRICS.md`](docs/METRICS.md).

## Стек

- **Nuxt 4** (статическая генерация, `nuxt generate`), **Vue 3** (`<script setup lang="ts">`)
- **TypeScript** (строгий), **Tailwind CSS v4**, **Bitrix24 UI** (`b24ui`) — первоисточник по
  «как правильно»: [`bitrix24/b24ui/AGENTS.md`](https://github.com/bitrix24/b24ui/blob/main/AGENTS.md)
  и [`llms.txt`](https://bitrix24.github.io/b24ui/llms.txt)
- **Bitrix24 JS SDK** (`@bitrix24/b24jssdk` + `-nuxt`) — встройка в портал;
  [`llms.txt`](https://bitrix24.github.io/b24jssdk/llms.txt). Точные REST-сигнатуры — MCP `b24-dev-mcp`
- **Vitest** — два проекта: `unit` (node, чистые функции) и `nuxt` (`@nuxt/test-utils` + happy-dom)


```
      │              │                │                        │
      ▼              ▼                ▼                        ▼
 /app/leads     /app/managers    /app/activity            /app  (выбор отчёта)
useReportData  useManagerReport  useActivityReport
      │              │                │
  metrics.ts   managerLoad.ts    activityLoad.ts

      └──────────────┼────────────────┘
```

Backend'а нет и не планируется: отчёт только читает CRM и считает на клиенте. Появится он тогда и
только тогда, когда объёмы перестанут влезать в выборку из фрейма — см. «Когда понадобится
backend».

### Ключевые решения

- **Знаменатель конверсий — параметр ядра, а не константа.** Формула одна — `Лиды − Брак`, как в
  ТЗ (решение владельца от 2026-09-04, переключатель из интерфейса убран). Параметром он остался
  потому, что вопрос уже разворачивался трижды, и каждый разворот стоил одну строку в
  `useReportData`, а не правку формул. История — [`docs/METRICS.md`](docs/METRICS.md).
- **Делим только через `share()`.** Пустой период — норма этого отчёта. `x / 0` в шаблоне печатает
  «NaN %», и отчёт перестают читать целиком.
- **Демо-набор задан ЛИДАМИ И СДЕЛКАМИ, а не итогами.** Итоги считает то же ядро, что и на живых
  данных, — поэтому они не могут разойтись между блоками. Ровно этот дефект и есть в макете
  (490 000 против 485 000).
- **Семантику стадий берём из справочника портала**, а не из кодов вроде `WON`/`LOSE`: клиент
  переименовывает стадии, и захардкоженный список молча посчитал бы чужую воронку неправильно.
  Проверено вживую: на тестовом портале стадий провала у сделки уже ДВЕ (`LOSE` и `APOLOGY`).
- **Причины проигрыша сводятся по НАЗВАНИЮ на границе с порталом, а не в ядре.** У заказчика
  четыре направления, и одна причина — это пять-шесть кодов стадий с разным регистром и тире
  вместо дефиса. Ядро группирует по идентификатору и о направлениях не знает: сделку помечает
  каноничный ключ из `app/utils/reasonMerge.ts`, одно сведение на прогон, только по стадиям
  провала. Разные названия НЕ сводятся, даже очевидно родственные («… (удалить)»): склеить разное
  хуже, чем не склеить одинаковое.
- **Фильтры по полям лида ложатся на сделки через список ID лидов.** У сделки нет ни менеджера
  лида, ни его стадии; в режиме счётчиков лиды поимённо неизвестны — поэтому под такими фильтрами
  отчёт сначала спрашивает ID лидов, потом сделки по ним кусками по 500. ⚠ `LEAD_ID: [0]` на
  боевом портале отдаёт сделки БЕЗ лида: пустой список — «сделок нет» без запроса, а не запрос.
- **Число без списка «тем же условием» — некликабельно.** Детализация по клику показывает
  записи ровно тем условием, что дало число; «источник не указан» — остаток арифметики,
  «просрочено» — из истории стадий, за ними такого списка нет, и они остаются числами. Список,
  не сходящийся с числом над ним, хуже отсутствия списка.
- **Детализацию открывает НАСТОЯЩИЙ слайдер портала**, а не панель внутри отчёта (решение
  владельца 2026-09-06, по образцу `client-bank-alfa-by`). ⚠ `openSliderAppPage` открывает
  ЗАРЕГИСТРИРОВАННЫЙ адрес обработчика (`/app`), а не произвольный путь: поэтому список рисуется
  на главной приложения (`ReportDrill.vue` внутри `app/pages/app/index.vue`), а не на своём
  адресе. Плейсмент под это не регистрируется — `place` едет параметром ВЫЗОВА, значит,
  переустановка боевых порталов не нужна.
- **Слайдер — отдельный фрейм, и условие едет туда САМОДОСТАТОЧНЫМ.** Состояния отчёта там нет:
  едет полный фильтр REST, охват сделок, направление и готовые подписи причин провала (их не
  собрать заново — каноничное имя сводится из стадий четырёх направлений).
- **⛔ Условие едет через `user.option`, а НЕ параметрами вызова.** Проверено на боевом:
  `PLACEMENT_OPTIONS` килобайтов не держит — короткий `place` доехал, JSON фильтра нет, и человек
  получил «Список не открылся» при исправном отчёте. Соседний `client-bank-alfa-by` доверяет
  этому каналу ровно ОДИН короткий скаляр и знает случай, когда `PLACEMENT_OPTIONS` приехал
  пустым целиком. Поэтому параметрами вызова едет только **короткий одноразовый ключ**, а условие
  ждёт в `user.option` портала — там же, где запоминается отбор. ⚠ Ключ одноразовый не для
  красоты: запись одна, и два быстрых клика перезаписали бы условие — слайдер первого скажет
  «условие устарело» вместо чужого списка под верным заголовком.
- **`PLACEMENT_OPTIONS` читаем терпимо: объектом ИЛИ JSON-строкой, ключ — без учёта регистра, и со
  вторым источником в адресе.** SDK кладёт их как есть (`placement.mjs`), форму задаёт портал, а
  остальные поля он шлёт заглавными. Наивное `options.drill` молча даёт «фрейм не детализация».
- **Условие разбирается проверяюще**, как сохранённый отбор: негодное отвергается целиком — и
  страница НАЗЫВАЕТ причину, а не показывает оглавление приложения тому, кто ждёт список. ⚠ Поля
  фильтра — по БЕЛОМУ СПИСКУ (`ALLOWED_FILTER_FIELDS`): позвать наш фрейм может любое приложение
  портала, а читать CRM оно будет нашим токеном. Новое условие в детализации — новое поле в
  списке, иначе список молча не откроется.
- **На телефоне у матрицы отчёта 2 своя раскладка, а не горизонтальная прокрутка.** Шестнадцать
  стадий в строку требуют 640 пикселей, на телефоне их 390: от таблицы был виден один столбец
  «Менеджер», числа уезжали за край, а прокрутку внутри карточки там не находят. До `md` — карточка
  на менеджера, с `md` — таблица; числа и списки за ними одни и те же, и это под тестом.
- **Вне портала детализации нет совсем** (решение владельца 2026-09-06): числа демо-страницы —
  обычный текст. ⚠ И не только вне фрейма: кликабельность гасится всегда, пока на экране
  ДЕМО-набор, — живая выборка могла упасть при исправном SDK, и клик открыл бы слайдер с
  фильтром, собранным из придуманных строк.
- **Менеджеров отчёта 2 перечисляем ПО СДЕЛКАМ, а не по `user.get`.** У уволенных сделки
  остаются, а список активных сотрудников их не отдаёт: матрица молча теряла бы целые столбцы
  работы. Перечисление — цепочка команд в одном пакете через `$result[...]`; исчерпанная цепочка
  идёт ПО ВТОРОМУ КРУГУ без единой ошибки, поэтому читать её можно только `readDistinctChain`
  (`docs/PORTAL.md`, «Перечисление менеджеров»).
- **Разрез отчёта 2 — это `MYCOMPANY_ID` сделки**, поле «Реквизиты вашей компании», а НЕ
  `COMPANY_ID` (компания-клиент). ⚠ Слово «офис» в проекте НЕ используется — ни на экране, ни в
  коде (решение владельца 2026-09-05): разрез называется «Моя компания». На боевом портале поле
  заполнено у 8 % открытых сделок, но группа «Не указана» — такая же, как все: она сортируется по
  числу сделок и не выделяется плашками, а выбор «смотреть её или нет» отдан фильтру. Две подписи
  одной группы: «Не указана» в таблице и легенде (рядом есть заголовок про «мою компанию»), «Без
  моей компании» в фильтре и заголовке списка. ⚠ `MYCOMPANY_ID: 0` — это ЗНАЧЕНИЕ («поле пусто»),
  а не «фильтра нет»: `filters.companyId ? …` молча превратило бы этот выбор во «все».
- **Период отчёта 2 обязателен, умолчание — текущий месяц.** «За всё время» убрано владельцем
  2026-09-05: в направлении заказчика 616 тысяч сделок. ⚠ Период считается по дате СОЗДАНИЯ
  сделки, и подпись под панелью обязана говорить «созданы»: иначе числа читаются как «сколько
  сейчас в работе», а это другой вопрос.
- **В кольцах отчёта 2 компании НЕТ — она выбирается фильтром, по одной за раз** (решение
  владельца 2026-09-05). Круг, поделённый между компаниями, отдавал одной почти всё — на боевом
  портале в сентябре это 599 сделок против одной, — и всё интересное сжималось в неразличимую
  штриховку по краю. Поэтому кольца — «менеджер → стадия», а компания стоит в заголовке блока.
- **Диаграмма отчёта 2 не растягивает детей на сектор родителя.** У компании бывают сделки вне
  строк (сотрудник не попал в перечисление); растянутый сектор показал бы 25 сделок как 30. Остаток остаётся пустым местом,
  хвост менеджеров сворачивается в некликабельный сектор «Остальные». Ключи узлов — те же, что у
  счётчиков ядра, поэтому клик по сектору открывает ТОТ ЖЕ список, что и число в таблице.
- **Подпись живёт В секторе, но решение «влезет ли» принимает компонент, а не геометрия.**
  Геометрия отдаёт размеры дуги, про шрифт знает только `SunburstChart.vue`: узкая дуга остаётся
  без подписи (текст поверх соседа хуже пустого сектора), длинное имя режется по ширине кольца. В
  секторе — «Фамилия И.», а не обрезанная строка: «Авдеева …» и «Авдеенко …» на соседних секторах
  выглядели бы одинаково, а это разные люди.
- **⛔ Постранично портал читает SDK, а не мы.** `AjaxResult.getData()` отдаёт
  `Object.freeze({ result, time })` — поля `next` там НЕТ ВОВСЕ, оно доступно только через
  `isMore()`/`getNext()`. Самодельный цикл по `start` читал `data.next`, всегда получал
  `undefined` и заканчивался после ПЕРВОЙ страницы: в отчёт попадали ровно 50 сотрудников, а
  остальные шли «Сотрудник #5562» — числа при этом верные, потому и не замечалось. Полные выборки
  — только `actions.v2.callList` (или `fetchList`).
- **⛔ У `callList` своя конвенция параметров, и она НЕ та, что в документации метода.** Листает он
  не по `next`, а курсором: дописывает `'>ID'` в **строчный** `params.filter`, ставит свой
  `order: { ID: 'ASC' }` и `start: -1`, а переданный `order` выбрасывает. Значит условия отбора
  обязаны лежать в строчном `filter` — даже там, где документация метода требует заглавный
  `FILTER` (как у `user.get`). ⚠ Замер на живом портале (2026-09-06): при обоих ключах сразу
  заглавный `FILTER` игнорируется ЦЕЛИКОМ — `ACTIVE` и `USER_TYPE` молча пропадают, и список
  приезжает вперемешку с ботами. Курсор `'>ID'` при этом `user.get` понимает — тем же замером
  проверено, иначе `callList` крутил бы первую страницу без конца. ⚠ И `ACTIVE` понимается только
  при JSON-транспорте: form-data шлёт `false` строкой, и оба прохода вернули бы одно и то же.
- **Замер боевого портала 2026-09-06: 92 работающих и 237 уволенных, 7 запросов на отчёт.** Дефект
  «первой страницы» стоил 229 фамилий из 329 — семь из десяти, при совершенно верных числах
  ([`docs/PORTAL.md`](docs/PORTAL.md)).
- **⚠ Стенды тестов обязаны быть НЕ ЩЕДРЕЕ SDK.** Прежний мок отдавал `next` из `getData()`, и
  тест на 60 сотрудников был зелёным при сломанном боевом. ⚠ И подмена метода SDK ЦЕЛИКОМ его
  конвенцию параметров не проверяет: то, куда `callList` кладёт курсор и уцелеют ли рядом наши
  условия, сторожит отдельный тест в `tests/filters.test.ts`, повторяющий преобразование SDK.
- **Уволенных читаем ВТОРЫМ проходом `user.get` (`ACTIVE: false`).** Портал по умолчанию отдаёт
  только работающих, а сделки уволенного остаются — ровно тот случай, ради которого менеджеры и
  перечисляются по сделкам. Без второго прохода строка подписана «Сотрудник #5562»: число верное,
  а чьё оно — непонятно. ⚠ «Уволен» и «не нашёлся» — РАЗНЫЕ вещи: пометка ставится только по
  признаку портала, иначе сбой чтения объявил бы уволенными всех подряд.
- **Ответственный у сделки обязателен** — замер 2026-09-05: ни одной из 689 523 сделок портала без
  него ([`docs/PORTAL.md`](docs/PORTAL.md), «Ответственный у сделки обязателен»). Поэтому плитки
  «Без ответственного» на экране нет (решение владельца 2026-09-06), а у остатка `unlisted`
  осталась ровно одна причина: сотрудник не попал в перечисление.
- **Итог компании — отдельный счётчик, а не сумма строк.** Счётчики приходят разными пакетами,
  между ними портал живёт, и сделка сотрудника, не попавшего в перечисление, в строки не
  попадёт. Разница показывается остатком («сделки вне строк», «прочие стадии»), а не прячется.
- **⛔ Две ОБРАТНЫЕ шкалы направления в одном отчёте 3.** У телефонии `CALL_TYPE: 1` — ИСХОДЯЩИЙ,
  у дел CRM `DIRECTION: 1` — ВХОДЯЩЕЕ. Имя фильтра `INCOMING` толкает прочитать первую наоборот, а
  документация значения не расшифровывает вовсе. Проверено на живом портале поимённо, на 38
  звонках через связанные дела. Перевод между шкалами живёт в ДВУХ соседних константах
  (`DEED_DIRECTION` и `CALL_TYPE_CODE` в `activityQuery.ts`) и закрыт тестом: перепутать — поменять
  местами два столбца, и по числам это НЕ ВИДНО, оба варианта правдоподобны. Сверяйтесь с
  [`docs/PORTAL.md`](docs/PORTAL.md), а не с памятью: эта пара уже была записана в доки задом
  наперёд.
- **Звонки отчёта 3 читаются СТРОКАМИ и фоном, а всё остальное — счётчиками.** `total` даёт только
  количество, а владельцу нужна сумма длительности, которой нет ни в каком агрегате телефонии.
  Месяц — 381 страница (читаем ВСЕ звонки: без порога в фильтре, иначе недозвоны не посчитать);
  читаются они ПАКЕТАМИ по 50 команд: 24 мс на страницу против 124 мс одиночными запросами, весь
  месяц за 5,7 с и восемь запросов (замер 2026-09-06). ⚠ Первая редакция утверждала обратное
  («пакет не ускоряет») — замер был неверен, и отчёт зря читал звонки минутами. Устройство от
  этого не изменилось: таблица показывается без звонков, а `callsKnown` говорит экрану ставить
  ПРОЧЕРК, а не ноль. Ноль читается как «не звонил». Период ограничен МЕСЯЦЕМ (решение владельца):
  звонки лежат строками в памяти фрейма.
- **Отдел отчёта 3 — это ПОДДЕРЕВО, а не строка списка.** У заказчика 43 отдела, 11 с подотделами,
  и люди сидят и в узлах, и в листьях: у 10 узлов из 11 сотрудники есть ПРЯМО в них. Один узел
  показал бы «Департамент распространения» как 37 человек вместо всех, кто там работает; одни
  листья — потеряли бы те же 37. Оба варианта дают правдоподобное число и неверный ответ. ⚠
  `UF_DEPARTMENT` — МАССИВ: 13 сотрудников числятся в нескольких отделах сразу.
- **⛔ Отдел применяется к звонкам ПОСЛЕ чтения.** У `voximplant.statistic.get` нет фильтра по
  отделу, телефония читается по всему порталу. Без отсева (`scopeCallsToUsers`) фильтр работал бы
  наполовину: сотрудник соседнего отдела исчезал бы строкой со счётчиками и возвращался бы строкой
  «Сотрудник #7» со своими звонками — человек, выбравший «Отдел закупок», видел бы в нём продавцов.
- **⛔ `department.get` листается СМЕЩЕНИЕМ, а не `callList`.** У метода нет параметра `filter`
  вовсе (фильтры плоские: `ID`, `NAME`, `PARENT`, `UF_HEAD`), а `callList` кладёт курсор `'>ID'`
  именно в строчный `filter`. Проверено на боевом: с `filter: {'>ID': 4085}` приехали 25 отделов с
  МЕНЬШИМ идентификатором — курсор не применился вообще. На портале с полусотней отделов это
  чтение одной и той же первой страницы без конца.
- **⛔ `voximplant.statistic.get` понимает только ЗАГЛАВНЫЙ `FILTER`.** Строчный он не отвергает —
  возвращает ВЕСЬ портал за всё время, и под заголовком «Разговоры · Иванов» открылись бы чужие
  звонки за годы. Курсор `>ID` он при этом понимает, поэтому список звонков листается курсором, а
  не смещением.
- **Условие списка отчёта 3 строят ТЕ ЖЕ функции, что задавали вопрос «сколько».** Не «такое же
  условие», а буквально то же (`activityQuery.ts`): поэтому список не может разойтись с числом над
  ним, пока они не разойдутся у самого портала. Сверено сквозняком на боевом — одиннадцать
  показателей, счётчик против длины списка, сходится всё.
- **Читаем классические `crm.lead.list` / `crm.deal.list`, а не `crm.item.list`.** У универсального
  метода для лидов `STATUS_ID` приезжает под именем `stageId`, а неизвестное поле в `select` он
  принимает без ошибки и просто возвращает записи без него — отчёт посчитал бы все лиды «в работе»
  и не подал ни одного сигнала.

### Палитра диаграмм

`--chart-1…12` (и парный `--chart-N-ink` — цвет подписи НА этом секторе) в
`app/assets/css/main.css` — ОТДЕЛЬНАЯ от семантических токенов b24ui, и это не самоволие.

⚠ `--ui-color-accent-main-success`/`-alert` в теме Битрикс24 — цвета **заливки**, а не «зелёный» и
«красный» вообще: тема так их и использует (`--ui-color-design-filled-success-bg`), поэтому на
светлом фоне как ТЕКСТ они дают порядка 2–3:1 при пороге 4.5:1. Секторам кольца при этом нужна не
читаемость текста, а различимость соседей, в том числе при дальтонизме, — другой критерий,
который семантические токены не проверяли никогда.

⚠ Двенадцать цветов, различимых ПОПАРНО при дальтонизме, не существуют — это проверено перебором,
а не предположено. Поэтому проверяются СОСЕДИ ПО КРУГУ: порядок слотов (`CHART_SLOTS` в
`app/utils/managerChart.ts`) подобран так, что рядом никогда не встают похожие. Худшая соседняя
пара — ΔE 37.1 при пороге 8, в обеих темах и в трёх моделях дальтонизма. ⚠ Порядок «просто по
возрастанию» даёт 7.1 и НЕ проходит: сам по себе набор цветов не гарантирует ничего, гарантирует
порядок.

Это не обещание в комментарии, а `tests/palette.test.ts`: он читает `main.css`, считает ΔE и
контрасты и краснеет, если порядок слотов или значение цвета поменяли, не перепроверив. Прежний
комментарий обещал ΔE 33.5 при фактических 7.1 — ровно потому, что проверять было нечем.

⚠ `--chart-N-ink` существует потому, что белым по жёлтому — 2.2:1: цвет подписи на секторе нельзя
взять один на всю палитру, он свой у каждого цвета (не ниже 4.3:1). ⚠ А у ВНЕШНЕГО кольца чернила
третьи — `--chart-ink-veiled`: оно рисуется полупрозрачным, подмешивает фон карточки, и на этом
посветлевшем цвете `--chart-N-ink` падает до 2.7:1. Зато смешение всегда идёт в сторону фона,
поэтому там хватает одного цвета на тему.

⚠ `--chart-muted` и `--chart-muted-strong` — НЕ палитра, а «это не человек»: ими закрашены сектора
«Остальные» и «Вне перечисления». Взять им слоты палитры нельзя — слотов ровно столько же,
сколько менеджеров в кольце, и тринадцатый сектор получил бы цвет первого, встав с ним рядом.

Три цвета в светлой теме идут ниже 3:1 к фону — это допустимо **ровно потому**, что кольцо никогда
не единственный носитель смысла: подпись стоит прямо в секторе, рядом легенда с числами и долями,
под ним полная таблица. Уберёте таблицу — палитра перестанет быть годной.

## Встройка в Битрикс24

Точка одна — `CRM_ANALYTICS_MENU`, и в ней ТРИ обработчика: `/app/leads`, `/app/managers` и
`/app/activity` (`PLACEMENTS` в `app/config/b24.ts`). Несколько обработчиков в одной точке портал
допускает; в единственном экземпляре регистрируются только `REST_APP_URI` и
`PAGE_BACKGROUND_WORKER`. Права: `crm`, `placement`, `user_brief`, `telephony`, `department`.

⚠ Установка СНАЧАЛА снимает свои привязки (в том числе прежние — `LEGACY_PLACEMENT_CODES`), потом
ставит заново: `placement.bind` с другим адресом ДОБАВЛЯЕТ пункт, а не заменяет, и без снятия в
меню оказалось бы три входа.

⚠ Заголовки и адреса пунктов применяются при `placement.bind`, то есть на УСТАНОВКЕ. На уже
установленных порталах пункт остаётся прежним, пока приложение не переустановят, — это не дефект
выката.

⚠ Раз пункты ведут прямо в отчёты, портал открывает POST-ом уже `/app/leads`, `/app/managers` и
`/app/activity`: они обязаны быть в `PORTAL_HANDLER_ROUTES` и в `error_page 405 =200` (nginx).

Контракт, порядок установки и типовые ошибки — [`docs/EMBEDDING.md`](docs/EMBEDDING.md).

⚠ Добавление права требует ПЕРЕсогласования на всех установленных порталах. Список в
`app/config/b24.ts` менять только вместе с владельцем; его сторожит `tests/b24Config.test.ts`.

## Когда понадобится backend

Сейчас его нет намеренно: отчёт читает CRM из фрейма и считает на клиенте — это быстрее в
разработке, дешевле в эксплуатации и не хранит данные клиента у нас. Backend понадобится, когда
появится хотя бы одно из:

- **объёмы. ⛔ ПОРОГ ПРОЙДЕН — замер по БОЕВОМУ порталу заказчика (2026-09-04).** Ответ клиента
  «до 5 000 в месяц» относился к ЛИДАМ. Сделок втрое больше:

  | Месяц | Лидов | Сделок |
  |---|---|---|
  | 2026-06 | 3 450 | 10 972 |
  | 2026-07 | 3 498 | 10 289 |
  | 2026-08 | 3 851 | 10 178 |

  Всего в портале 210 186 лидов и 716 972 сделки; строками месяц выбирался бы ≈ 2,5 минуты.
  ✅ Решено БЕЗ backend'а: лиды приходят СЧЁТЧИКАМИ (`total` по фильтру, ~100 вопросов тремя
  пакетами ≈ 3 с), строками читаются только сделки ИЗ ЛИДОВ (каждая десятая), остальные сделки —
  тремя счётчиками для контекста. Месяц ≈ 17 с. Ядро при этом одно: `aggregateLeads` сворачивает
  строки демо-набора в тот же агрегат, что приходит с портала. Замер и что из него следует —
  [`docs/PORTAL.md`](docs/PORTAL.md);
- расписание — отчёт «на почту каждый понедельник»;
- сравнение периодов с историей, которой в CRM уже нет;
- экспорт в Excel/PDF на сервере (клиентский экспорт backend'а не требует).

Пока ничего из этого не заявлено — не заводим.

## Конвенции

- **Пользовательский текст, README и документация — на русском.** Комментарии и JSDoc — тоже:
  весь код здесь русскоязычный, и смешение языков ВНУТРИ модуля — настоящий дефект чтения.
- Чистые функции — `app/utils/*`, данные и константы — `app/config/*`, типы — `app/types/*`,
  реактивная логика — `app/composables/*`, UI — компоненты и страницы. **Всё в `utils` покрываем
  тестами.**
- Данные из API рендерим только через `{{ }}` (авто-экранирование) — никакого `v-html`.
- **Issue, Pull Request и всё, что видит заказчик на GitHub, — на русском.** Читает их владелец и
  клиент, а не только разработчики: issue на английском для них — это ещё один барьер там, где его
  быть не должно. На английском остаются только технические маркеры (`Last reviewed`, коды
  плейсментов, имена методов REST) и сам код.
- **Комментарий объясняет ПОЧЕМУ, а не ЧТО.** `// увеличиваем счётчик` не нужен; нужно то, что
  нельзя восстановить из кода: какой дефект здесь уже был, почему выбран этот вариант, что
  сломается при «очевидном» упрощении.
- **В `main` не пушим — только через PR с зелёным CI.**

Штамп ревью: каждый `.md` в корне и `docs/` несёт строку `> Last reviewed: YYYY-MM-DD`
блок-цитатой сразу под заголовком H1. Ключ `Last reviewed` всегда на английском (технический
маркер). Дату бампим только при содержательном изменении. Наличие штампа проверяет
`tests/mdReviewStamp.test.ts`.
