# some-report — отчёты по CRM для Битрикс24

> Last reviewed: 2026-09-05

Приложение Битрикс24 с ДВУМЯ отчётами по CRM. Встраивается в раздел **CRM-аналитика** портала и
открывается там же, где штатные отчёты. Nuxt 4 (SSG), данные только читает.

Пункт меню открывает главную страницу приложения (`/app`) — выбор отчёта:

| Отчёт | Адрес | На какой вопрос отвечает |
|---|---|---|
| **Аналитика по лидам** | `/app/leads` | путь лида от поступления до закрытия сделки |
| **Сделки по менеджерам** | `/app/managers` | сколько сделок у каждого менеджера в каждом офисе и на какой стадии |

> **Статус:** приложение выкачено, встроено в портал заказчика и считает **живые** данные: лиды
> счётчиками, сделки из лидов строками, месяц около 15 секунд; второй отчёт — счётчиками, около
> 16 секунд на направление. Вне портала (`?preview=1`) — демо-набор, и экран говорит об этом
> прямо. Решения по формулам — [`docs/METRICS.md`](docs/METRICS.md), ТЗ — [`docs/TZ.md`](docs/TZ.md).

## Отчёт 1 «Аналитика по лидам»: что показывает

1. **Сводка** — лиды, брак, квалифицировано, успешные сделки, конверсии, выручка.
2. **Воронка** — Лиды → Квалифицировано → Успешные сделки.
3. **Брак лидов по причинам** — кольцевая диаграмма и таблица.
4. **Причины проигрыша сделок** — количество и потерянная выручка по каждой.
5. **Эффективность источников** — по каждому источнику лиды, брак, конверсии, выручка; отдельным
   блоком — топ-5 источников по количеству лидов с теми же колонками.
6. **Обработка лидов и потери до сделки** — обработано, просрочено, среднее время первого ответа.
7. **Успешные сделки без связи с лидом** — для справки, по дате закрытия, с суммами и источниками.

Фильтры над отчётом: источник, менеджер (ответственный лида), стадия лида, причина закрытия лида,
причина проигрыша сделки. На блок 7 они не действуют — он сам об этом говорит.

Числа кликабельны: за каждым — слайдер со списком записей тем же условием и ссылками на карточки
в CRM портала. Кликабельно только то, за чем такой список есть: «источник не указан» и
«просрочено» остаются числами.

Экспорт — кнопки **Excel** (лист на каждый блок, те же числа, что на экране) и **PDF** (снимок
всего дашборда одной страницей). Оба файла собираются в браузере, сервера нет.

## Отчёт 2 «Сделки по менеджерам»: что показывает

Таблица на каждый офис: строка — менеджер, столбец — стадия, в клетке — сколько сделок. Офис здесь
— поле сделки **«Моя компания»** (`MYCOMPANY_ID`), а не компания-клиент. Сверху — сводка: сделок,
менеджеров, офисов, стадий в таблице.

Отбор: **направление** (одно, у направлений разные стадии), **охват** («в работе» по умолчанию,
«успешные», «провальные», «все стадии») и **период создания** сделки («за всё время» по умолчанию).

Числа кликабельны: за каждым — список сделок ровно тем же условием и ссылки на карточки в CRM.
Числа-остатки — «сделки вне строк» и «прочие стадии» — не кликабельны: списка за ними нет, и
притворяться ссылкой они не должны. Что это за остатки — [`docs/METRICS.md`](docs/METRICS.md).

Строк отчёт не читает вообще: на боевом портале 698 тысяч сделок, поэтому он задаёт порталу
вопросы «сколько» — по одному на клетку, пакетами по 50 (замер — [`docs/PORTAL.md`](docs/PORTAL.md)).

## ⚠ Главное, что нужно знать про числа

ТЗ и согласованный макет считают конверсии по РАЗНЫМ знаменателям и дают на одних и тех же данных
разный результат:

| | Знаменатель | Лид → сделка | Лид → продажа |
|---|---|---|---|
| ТЗ | лиды без брака (1 000) | **100 %** | **62 %** |
| Макет | все лиды (1 250) | **80 %** | **49,6 %** |

✅ Решено 2026-09-04: считаем **по ТЗ**, от лидов без брака. Переключателя в отчёте больше нет —
два ответа на один вопрос рядом с заголовком подрывали доверие к числу. История спора —
[`docs/METRICS.md`](docs/METRICS.md).

## ⚠ Два блока ТЗ на портале пока не посчитать

Замер живого портала показал: причин брака лида и причин проигрыша сделки в Битрикс24 **нет ни
полем, ни справочником** — стадия брака одна, пользовательских полей ноль. Пока администратор
портала не заведёт стадии или поле-список, эти два блока покажут по одной строке. Что именно
завести и какой вариант лучше — [`docs/PORTAL.md`](docs/PORTAL.md).

## Быстрый старт

```bash
corepack enable && pnpm install
pnpm dev            # http://localhost:3000
```

Страницы приложения (`/app/leads`, `/app/managers`, `/install`) вне портала Битрикс24 закрыты
заглушкой — открывайте их с `?preview=1`. Это штатный обход для разработки, скриншотов и тестов.
Главная приложения (`/app`) открыта всегда: данных портала она не показывает.

## Требования

- **Node.js 22 LTS**
- **pnpm** (через corepack; версия закреплена в `packageManager` в `package.json`)

## Команды

```bash
pnpm lint         # ESLint
pnpm typecheck    # два прохода: приложение + тесты
pnpm test         # Vitest (unit + nuxt)
pnpm check        # lint + typecheck + test — основная часть проверок CI
pnpm generate     # сборка статики → .output/public
pnpm smoke        # после generate: открыть сборку браузером под боевым CSP (в CI — отдельный шаг)
pnpm smoke:image http://localhost:8080   # то же на поднятом контейнере из образа
```

Перед пушем прогоняйте `pnpm check`.

## Деплой

Статика собирается в Docker-образ (`nginxinc/nginx-unprivileged`) и публикуется в GHCR; на сервере
контейнер поднимается из [`deploy/docker-compose.prod.yml`](deploy/docker-compose.prod.yml) за общим
nginx-proxy (TLS — Let's Encrypt), дальше обновления подхватывает Watchtower. Шаги, диагностика и
проверки — [`docs/DEPLOY.md`](docs/DEPLOY.md).

⚠ Первый запуск контейнера — **ручной шаг**: Watchtower только обновляет существующие контейнеры.
Пока его не сделали, домен отдаёт 503.
