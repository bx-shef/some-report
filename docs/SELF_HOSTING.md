# SELF_HOSTING.md — своя копия: от клона до отчёта в портале

> Last reviewed: 2026-09-16

Пошагово: как развернуть **свою** копию приложения — на своём домене, из своего репозитория, для
своего портала Битрикс24. Инструкция рассчитана на то, что читатель видит проект впервые.

Каждый шаг заканчивается проверкой «получилось или нет». Проверки не пропускайте: половина ошибок
выката в этом проекте выглядит как исправная работа — портал показывает пустую область, и ни в
одном логе нет ни строчки.

Про сам продукт — отчёты, формулы, что есть в портале — читайте [`README.md`](../README.md) и
[`METRICS.md`](METRICS.md). Здесь только развёртывание.

---

## Что должно быть до начала

| Что | Зачем | Как проверить |
|---|---|---|
| Аккаунт GitHub | репозиторий и сборка образа | — |
| Сервер с Docker | там будет жить контейнер | `docker --version` |
| Общая инфраструктура на сервере | маршрутизация по домену, сертификаты, автообновление | команды в шаге 6 |
| Домен или поддомен | адрес приложения | доступ к DNS-записям |
| Портал Битрикс24 | куда встраиваемся | права администратора портала |
| Node 22 + pnpm (локально) | прогнать проверки перед выкатом | `node -v`, `pnpm -v` |

⚠ **Приложение не хранит данные и не имеет backend'а.** Оно отдаёт статику, а данные читает из CRM
прямо в браузере пользователя, правами того, кто открыл отчёт. Поэтому серверу не нужны ни база, ни
доступ к порталу — только раздать файлы по HTTPS.

## Шаг 1. Сделать репозиторий своим

Форк или обычный клон с пушем в свой новый репозиторий — разницы для дальнейшего нет.

```bash
git clone https://github.com/bx-shef/some-report.git my-report
cd my-report
git remote set-url origin https://github.com/<ВАШ-АККАУНТ>/<ВАШ-РЕПОЗИТОРИЙ>.git
git push -u origin main
```

Локально поставьте зависимости и прогоните проверки — они должны быть зелёными ДО любых правок:

```bash
pnpm install
pnpm check      # линтер, типы, тесты
```

**Проверка шага:** `pnpm check` завершается без ошибок, во вкладке **Actions** вашего репозитория
прогон запустился.

⚠ У форков GitHub Actions по умолчанию **выключены**. Если во вкладке Actions пусто — включите их
там же одной кнопкой, иначе образ никогда не соберётся, а причина будет неочевидна.

## Шаг 2. Заменить то, что осталось от прежнего владельца

Пять мест. Меньше пяти — что-нибудь молча не заработает.

| Где | Что там сейчас | На что менять |
|---|---|---|
| `Dockerfile`, `ENV B24_PORTAL_ORIGINS` | `… https://bitrix.ankron.by` | адрес **вашего** коробочного портала |
| `tests/nginxConf.test.ts` | проверка, что этот адрес есть в образе | тот же ваш адрес |
| `deploy/docker-compose.prod.yml`, `image:` | `ghcr.io/bx-shef/some-report:latest` | `ghcr.io/<ваш-аккаунт>/<ваш-репозиторий>:latest` |
| `deploy/.env.example`, `DOMAIN` | `some-report.bx-shef.by` | ваш домен |
| `package.json` — `homepage`, `repository`, `bugs` | ссылки на прежний репозиторий | ваши |

### Про домены порталов — самое важное место

`B24_PORTAL_ORIGINS` — это список тех, кому разрешено встраивать приложение в свой фрейм И кому оно
имеет право отвечать. Он уходит сразу в две директивы заголовка безопасности: `frame-ancestors` и
`connect-src`.

**Облачные порталы уже покрыты** шаблонами по зонам (`https://*.bitrix24.ru`, `https://*.bitrix24.by`
и так далее) — если ваш портал облачный, менять вообще ничего не нужно, только уберите чужой адрес.

**Коробочный портал живёт на своём домене** и ни под один шаблон не подходит — его добавляют в этот
список руками:

```dockerfile
ENV B24_PORTAL_ORIGINS="https://*.bitrix24.ru … https://portal.вашдомен.ru"
```

⚠ **Забытый коробочный домен даёт пустую область на месте отчёта — без единой ошибки на экране и
без строчки в логах сервера.** Заголовок присылает сервер, нарушение фиксирует браузер. Это самый
дорогой в диагностике класс ошибок в этом проекте, поэтому список и закрыт тестом.

⚠ Тест `tests/nginxConf.test.ts` («коробочный портал заказчика есть в списке образа») специально
падает, когда домен пропал из `Dockerfile`. Поменяйте в нём адрес на свой — **не удаляйте саму
проверку**: она существует ровно затем, чтобы никто не выкатил образ без домена своего клиента.

**Проверка шага:**

```bash
pnpm check                                  # тесты зелёные с вашими адресами
grep -c "bitrix.ankron.by\|bx-shef" Dockerfile deploy/docker-compose.prod.yml   # везде 0
```

## Шаг 3. Домен и DNS

Заведите `A`-запись на IP сервера. Сертификат выпишется сам на шаге 7 — заранее ничего делать не
нужно.

**Проверка шага:** `dig +short report.вашдомен.ru` возвращает IP вашего сервера.

## Шаг 4. Сказать сборке, по какому адресу живёт приложение

**Settings → Secrets and variables → Actions → вкладка Variables** (именно Variables, а не Secrets:
адрес публичный).

| Имя | Значение |
|---|---|
| `NUXT_PUBLIC_SITE_URL` | `https://report.вашдомен.ru` |

⚠ Это **build-time** значение: статическая сборка запекает его в файлы. Поменять его на работающем
сервере нельзя — нужна пересборка образа.

⚠ Зачем оно вообще: из этого адреса страница установки строит **абсолютный** адрес обработчика для
портала. Относительный Битрикс24 не примет. Без переменной сборка **падает намеренно** — иначе
получился бы образ, который выглядит рабочим и молча не устанавливается в портал.

⚠ Значение обязано совпасть с `DOMAIN` из шага 7, буква в букву. Разойдутся — страница установки
пропишет в портал чужой адрес, и портал откроет пустоту.

**Проверка шага:** переменная видна в списке Variables и написана со схемой `https://`, без слэша на
конце.

## Шаг 5. Собрать образ и открыть к нему доступ

Сборка запускается сама на каждый пуш в `main`. Если правки из шага 2 уже запушены — она идёт.
Принудительно: **Actions → CI/CD → Run workflow** на ветке `main`.

Прогон делает три вещи: проверяет код, собирает образ и **проверяет уже собранный образ браузером** —
открывает страницы под боевым заголовком безопасности и пробует встроить их с чужого домена.

**Проверка шага:** в разделе **Packages** вашего репозитория появился пакет с тегом `latest`.

⚠ **Если ваш репозиторий приватный, пакет тоже будет приватным**, и сервер не сможет его скачать:
`docker compose pull` ответит `denied`. Варианты — открыть пакет (**Package settings → Change
visibility → Public**) или заранее залогинить сервер в GHCR токеном с правом `read:packages`. Шаг 7
без этого не пройдёт, а сообщение об ошибке на причину не намекает.

## Шаг 6. Проверить инфраструктуру на сервере

Приложение — обычный контейнер за общим обратным прокси. Эта инфраструктура **одна на весь сервер**
и к проекту не относится: если у вас уже крутятся другие сайты по такой схеме, всё на месте.

```bash
docker network ls | grep proxy-net
docker ps --format '{{.Names}}' | grep -E 'nginx-proxy|acme|watchtower'
```

Нужны:

- сеть `proxy-net`;
- `nginx-proxy` + `acme-companion` — маршрутизация по домену и сертификаты Let's Encrypt;
- Watchtower, запущенный с `--label-enable` — забирает новые образы (нужен со следующего выката).

⚠ Нет сети `proxy-net` — следующий шаг упадёт с `network proxy-net declared as external, could not
be found`. Поднимать эту инфраструктуру — отдельная задача, не часть этого проекта.

⚠ Второй Watchtower поднимать **не нужно**: он конфликтует по имени контейнера и плодит двойные
перезапуски.

**Проверка шага:** обе команды что-то вывели.

## Шаг 7. Первый запуск контейнера

⚠ **Этот шаг легко пропустить, и тогда всё выглядит сломанным.** Watchtower умеет только обновлять
уже существующие контейнеры — создавать новые он не умеет. Пока контейнер не поднят руками хотя бы
раз, на домен отвечает **503**: маршрута к нему у прокси просто нет. Со стороны это неотличимо от
«выкат не сработал», хотя образ лежит в реестре и исправен.

```bash
mkdir -p /home/bitrix/my-report && cd /home/bitrix/my-report

BASE=https://raw.githubusercontent.com/<ВАШ-АККАУНТ>/<ВАШ-РЕПОЗИТОРИЙ>/main/deploy
curl -fsSLO "$BASE/docker-compose.prod.yml"
curl -fsSL  "$BASE/.env.example" -o .env.example

cp .env.example .env && nano .env      # DOMAIN и, если нужно, LETSENCRYPT_EMAIL

docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml ps
```

⚠ `curl -f` здесь не украшение: без него сервер молча запишет в файл HTML-страницу ошибки GitHub, а
`docker compose` потом отругается на «невалидный YAML» — и искать будут поломку compose, а не то,
что файл не скачался.

⚠ `.env.example` качается с явным `-o`: у `curl -O` имя берётся из адреса, а файл начинается с
точки — в каталоге он окажется скрытым, и `ls` покажет пустоту там, где всё на месте.

⚠ `DOMAIN` обязан совпадать с `NUXT_PUBLIC_SITE_URL` из шага 4.

⚠ `docker compose ps` — разовый снимок, он не ждёт. Сразу после запуска честно покажет `starting`.
Подождите секунд пятнадцать и повторите.

Сертификат выпишется сам через десяток-другой секунд. Пока его нет, HTTPS отвечает ошибкой TLS вида
`unrecognized name` — это нормально ровно до первого выпуска.

**Проверка шага:** `docker compose ps` показывает `healthy`.

## Шаг 8. Проверить, что приложение раздаётся

```bash
# 1. Статика отвечает
curl -sI https://report.вашдомен.ru/ | head -1                      # HTTP/2 200

# 2. Служебные страницы попали в сборку
curl -sI https://report.вашдомен.ru/install/ | head -1              # 200
curl -sI https://report.вашдомен.ru/app/leads | head -1             # 200

# 3. Портал открывает обработчик POST-запросом — 405 быть не должно
curl -sI -X POST https://report.вашдомен.ru/app/leads | head -1     # 200, НЕ 405

# 4. Заголовок безопасности на месте и знает ваш портал
curl -sI https://report.вашдомен.ru/ | tr ';' '\n' | grep frame-ancestors
```

В последней строке обязан быть домен вашего портала. **Нет его — дальше идти бессмысленно:** портал
покажет пустую область вместо отчёта и ничего об этом не скажет.

Посмотреть отчёты глазами до установки в портал можно с параметром `?preview=1` — откроется
демонстрационный набор данных, и экран прямо говорит, что данные ненастоящие:

```
https://report.вашдомен.ru/app/leads?preview=1
```

**Проверка шага:** все четыре команды отвечают как указано, демо-страница открывается.

## Шаг 9. Зарегистрировать приложение в портале

В портале: **Приложения → Разработчикам → Другое → Локальное приложение**.

| Поле карточки | Значение |
|---|---|
| Путь вашего обработчика | `https://report.вашдомен.ru/app` |
| Путь для первоначальной установки | `https://report.вашдомен.ru/install` |
| Права доступа | `crm`, `placement`, `user_brief`, `telephony`, `department` |
| «Использует только API» | **снять галочку** |

⚠ **Галочку «Использует только API» надо именно СНЯТЬ.** С ней приложение объявляется как не
имеющее интерфейса: портал не откроет ни установщик, ни страницы отчётов, и виджеты для него
показываться не будут.

⚠ Обработчик — именно `/app`, **без отчёта в пути**: это главная приложения, с неё человек выбирает
отчёт. Адреса — абсолютные, по HTTPS, домен тот же, что в `NUXT_PUBLIC_SITE_URL` из шага 4.
Разойдутся — установка привяжет пункт на один домен, а карточка будет открывать другой.

⚠ **Права нужны все пять.** Без `crm` и `placement` пункт в CRM-аналитике вообще не
зарегистрируется (`ERROR_PLACEMENT_NOT_FOUND`); без `user_brief` останется пустым список сотрудников
в фильтре; без `telephony` и `department` отчёт «Активность пользователей» работает вполсилы — ни
звонков с длительностью, ни фильтра по отделам.

⚠ Добавление права потом потребует **переустановки** приложения на портале: список прав
согласовывается один раз, при первой установке.

⚠ Добавить и установить локальное приложение может только **администратор портала**.

Подробности каждого поля и разбор типовых ошибок — в [`EMBEDDING.md`](EMBEDDING.md).

**Проверка шага:** приложение появилось в списке локальных приложений портала.

## Шаг 10. Установить и проверить

Откройте приложение в портале — установка пройдёт сама: страница установки зарегистрирует пункты
меню и сообщит результат. Она же покажет, чего не хватает, если что-то пошло не так.

После установки в разделе **CRM → Аналитика** появятся три пункта:

- «Аналитика по лидам»;
- «Сделки по менеджерам»;
- «Активность пользователей».

**Проверка шага:** пункты видны в меню, отчёт открывается и показывает **ваши** числа, а не
демонстрационные.

⚠ Первый отчёт на большом портале считается не мгновенно: он читает CRM десятками запросов.
Ориентиры по времени — в [`README.md`](../README.md) и [`PORTAL.md`](PORTAL.md).

Не видно пунктов меню или на их месте пустая область — разбор по шагам в
[`EMBEDDING.md`](EMBEDDING.md), раздел «Установил — а отчёта нет».

## Дальше: как выкатывать обновления

```bash
git push origin main     # и всё
```

больше ничего делать не нужно — кроме случая, когда меняется `NUXT_PUBLIC_SITE_URL` или домен.

Подробности сборки, содержимое образа и проверки после выката — в [`DEPLOY.md`](DEPLOY.md).

## Если что-то пошло не так

| Симптом | Скорее всего | Где читать |
|---|---|---|
| На домене **503** | контейнер не поднят руками ни разу | шаг 7 |
| `docker compose pull` → `denied` | пакет приватный, сервер не авторизован | шаг 5 |
| В портале **пустая область** вместо отчёта | домена портала нет в `B24_PORTAL_ORIGINS` | шаг 2, [`EMBEDDING.md`](EMBEDDING.md) |
| Портал открывает обработчик и получает **405** | статика не принимает POST | шаг 8 |
| Установка прошла, **пунктов меню нет** | не те права или не тот адрес обработчика | [`EMBEDDING.md`](EMBEDDING.md) |
| Страница установки: **«адрес не задан»** | не задан `NUXT_PUBLIC_SITE_URL` при сборке | шаг 4 |
| Отчёт открывается, но числа **чужие** | открыт предпросмотр (`?preview=1`) | шаг 8 |
| Сборка падает на проверке доменов | остался чужой адрес или не поправлен тест | шаг 2 |
