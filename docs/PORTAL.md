# PORTAL.md — что реально есть в портале

> Last reviewed: 2026-09-08

Замер по живому REST тестового портала (только чтение). Это НЕ предположения:
каждое утверждение ниже получено запросом. Документ отвечает на вопрос «а посчитается ли вообще
то, что просит ТЗ» — и по двум блокам ответ отрицательный.

⚠ Ключ доступа в репозиторий не попадает и попасть не должен: он живёт в переменной окружения
разработчика. В коде, тестах и CI его нет.

## Итог одной строкой

**Четыре из шести блоков ТЗ считаются на текущем портале как есть. Два — не считаются вообще:
данных, которые они требуют, в Битрикс24 нет ни поля, ни справочника.**

## Что мешает (по убыванию важности)

### 1. Причин брака лида не существует как данных

Справочник стадий лида на портале:

| Код | Имя | Семантика |
|---|---|---|
| `NEW` | Не обработан | — |
| `IN_PROCESS` | В работе | — |
| `PROCESSED` | Обработан | — |
| `CONVERTED` | Качественный лид | `S` (успех) |
| `JUNK` | Некачественный лид | `F` (провал) |

Стадия брака **одна**. Пользовательских полей у лида **ноль** (`crm.lead.fields` → ни одного
`UF_`). Отдельного системного поля «причина отказа» у лида в Битрикс24 **нет** — есть только
свободный текст `STATUS_DESCRIPTION`, по которому группировать нельзя.

Значит блок ТЗ **«Брак лидов: дубль / спам / нецелевой запрос / сервисное обращение»** сейчас
посчитать не из чего. Отчёт покажет одну строку «Некачественный лид — 100 %».

**Что нужно сделать в портале** (выбирает заказчик, работа администратора, не разработчика):

- **Вариант А — стадии.** Завести четыре пользовательские стадии лида с семантикой «провал»:
  «Дубль», «Спам», «Нецелевой запрос», «Сервисное обращение». Тогда брак = все стадии с
  семантикой `F`, а причина = сама стадия. Отчёт при этом уже готов: он читает справочник
  портала, а не зашитый список.
  *Плюс:* менеджер закрывает лид одним действием. *Минус:* стадий в воронке станет больше.
- **Вариант Б — поле-список.** Одно пользовательское поле «Причина отказа» на лиде, обязательное
  при переводе в `JUNK`. *Плюс:* воронка не разрастается. *Минус:* два действия вместо одного, и
  поле легко оставить пустым — в отчёте появится строка «Причина не указана».

Рекомендую **вариант А**: он не даёт менеджеру закрыть лид, не назвав причину.

### 2. Причин проигрыша сделки тоже не существует как данных

Стадии сделки: `NEW`, `PREPARATION`, `PREPAYMENT_INVOICE`, `EXECUTING`, `FINAL_INVOICE`,
`WON` (`S`), `LOSE` (`F`), `APOLOGY` (`F`). Пользовательских полей у сделки — **ноль**. Поля
«причина проигрыша» в Битрикс24 нет.

Значит блок ТЗ **«Разбивка причин проигрыша: цена / срок поставки / купил у другого / не можем
поставить / прочее»** сейчас посчитать не из чего.

Решение то же: либо стадии с семантикой `F` по числу причин, либо поле-список на сделке.

⚠ Заодно это подтверждает решение в коде: «проиграна» определяется **по семантике**, а не по коду
`LOSE`. Стадий провала на портале уже две (`LOSE` и `APOLOGY`), и зашитый список кодов потерял бы
половину проигранных сделок.

### 3. Сделки не связаны с лидами (тестовый портал)

> На боевом портале заказчика связь ЕСТЬ — у 10 % сделок; остальные 90 % отчёт показывает
> блоком 7 «Успешные сделки без связи с лидом» (#12, #29). Ниже — картина тестового портала, где связи нет
> ни у одной сделки.

Все четыре сделки портала имеют `LEAD_ID` пустым. Пока связи нет:

- «Квалифицировано в сделку» = 0, потому что квалификация определяется наличием сделки у лида;
- вся выручка попадает в «сделки без лида-родителя» и не раскладывается по источникам.

Это нормально для тестового портала, где сделки заводили руками. Но на портале заказчика нужно
проверить то же самое: если менеджеры создают сделки не конвертацией лида, а с нуля, **воронка
ТЗ не соберётся** — связывать будет нечем.

### 4. Валюты разные, и это уже реальность

`crm.currency.list` портала:

| Валюта | Базовая | Курс |
|---|---|---|
| BYN | да | 1.0000 |
| RUB | нет | 3.5300 за 100 |
| USD | нет | 2.1400 за 1 |
| EUR | нет | 2.4400 за 1 |

Сделки на портале уже в разных валютах (есть и BYN, и RUB). Складывать `OPPORTUNITY` без
приведения нельзя — сумма получится бессмысленной, но выглядеть будет как обычное число.

Хорошая новость: приводить есть чем и без справочника курсов на нашей стороне —
`сумма в базовой = OPPORTUNITY × AMOUNT / AMOUNT_CNT`. Открытый вопрос остаётся только один: курс
на **дату сделки** или **текущий**. REST отдаёт текущий; курс на дату потребовал бы хранить
историю, то есть backend.

## Что работает и как это читать

### Семантика приезжает готовой

`crm.lead.list` отдаёт `STATUS_SEMANTIC_ID` (`P` в работе / `S` успех / `F` провал), а
`crm.deal.list` — `STAGE_SEMANTIC_ID`. То есть **справочник статусов нужен только для ИМЁН**, сама
классификация приходит вместе с записью. Это заметно упрощает адаптер и убирает целый класс
ошибок.

### ⚠ Ловушка `crm.item.list`: неизвестное поле в `select` молча возвращает пустоту

Универсальный `crm.item.list` для лидов (`entityTypeId=1`) **переименовывает** поля:
`STATUS_ID` приезжает как **`stageId`**, а не `statusId`. Запрос с `select: ["statusId"]` **не
даёт ошибки** — он возвращает записи, у которых поле просто отсутствует. То есть отчёт получил бы
пустые статусы и посчитал бы всё как «в работе», не сообщив ни о чём.

Отсюда два правила для адаптера:

1. Для лидов и сделок брать **классические** `crm.lead.list` / `crm.deal.list` — там имена полей
   совпадают с документацией и со справочниками.
2. Если всё же понадобится `crm.item.list` — проверять, что запрошенные поля ДЕЙСТВИТЕЛЬНО
   пришли, а не полагаться на молчание метода.

### Права

Вебхук отдаёт скоупы `crm`, `user`, `userfieldconfig` и прочие — то есть чтения CRM хватает.
Приложению (не вебхуку) мы просим `crm`, `placement`, `user_brief`; лишнего не нужно.

## Объёмы

На тестовом портале 8 лидов и 4 сделки — по ним о производительности судить нельзя. Порядок цифр
портала заказчика надо выяснить отдельно: от него зависит, хватит ли выборки из фрейма или
понадобится backend (см. «Когда понадобится backend» в `CLAUDE.md`).

## Проверено адаптером на живых данных

Адаптер (`app/utils/b24Adapter.ts`) прогнан по этому же порталу — от ответов REST до посчитанного
отчёта. Прогон подтвердил каждое утверждение выше, а не только пересказал их.

⚠ **Это НЕ значит, что живая выборка уже подключена.** Прогон делался разовым скриптом по вебхуку:
данные забирались отдельно и подавались адаптеру на вход. Сам `b24Adapter.ts` — чистая функция без
единого сетевого вызова; ходить в портал через `b24jssdk` будет `useReportData.ts`, и это
следующий шаг. Приложение по-прежнему показывает демонстрационные данные.

| Что проверяли | Результат |
|---|---|
| Валюта отчёта | `BYN` — базовая валюта портала определилась верно |
| Конвертация | сделка на 456 000 RUB превратилась в **16 097 BYN** (курс 3,53 за 100, а не за 1) |
| Обе стадии провала | в разбивку попали и «Сделка провалена», и «Анализ причины провала» — зашитый `LOSE` потерял бы половину |
| Лиды «сконвертирован» без сделки | **7 из 8** — ровно тот случай, который описан в §3. В отчёте они попадают в «Потери до сделки», а НЕ в «квалифицировано» |
| Сделки без лида-родителя | **4 из 4** — в разрез источников не попала ни одна |
| Сходимость | сумма лидов по источникам (7 + 1) совпала со сводкой (8) |
| Ни одного `NaN` | ни в долях, ни в суммах |

⚠ Строка «квалифицировано: 0» на этом портале — **не дефект отчёта**, а прямое следствие §3: связи
лид → сделка нет ни у одной сделки, а квалификация определяется именно ею. Отчёт честно
показывает ноль и отдельно сообщает, что 7 лидов помечены сконвертированными без сделки.

### История стадий лидов (замер 2026-09-04)

`crm.stagehistory.list` с `entityTypeId: 1` — источник времени первого ответа для блока 6.

| За август | Записей |
|---|---|
| всего | 9 738 |
| `TYPE_ID = 1` (создание) | ≈ 3 851 — по одной на лид |
| `TYPE_ID = 2` (переход) | 1 744 |
| `TYPE_ID = 3` (закрытие) | 4 143 |
| переходов в «Взято в работу» (`STATUS_ID = 1`) | 1 363 |
| лидов августа до сих пор в `NEW` | 2 |

Отчёт выбирает `ID, TYPE_ID, OWNER_ID, CREATED_TIME, STATUS_ID` — у лидов стадия называется
`STATUS_ID`, не `STAGE_ID`. Курсор по `>ID` с `start: -1` и фильтр `TYPE_ID: [2, 3]` работают.
Стадии лида портала: `NEW` «НОВАЯ ЗАЯВКА», `1` «ВЗЯТО В РАБОТУ», `CONVERTED` (успех), четыре

⚠ В отличие от `crm.lead.list`, метод отдаёт строки не в `result`, а в `result.items` — обёртку
универсальных методов. Выборка отчёта понимает оба конверта; при добавлении нового метода это
первое, обо что спотыкаются.

Запросов истории на период два: переходы и закрытия (`TYPE_ID: [2, 3]`, основная масса) и
создания сразу в стадии не-`NEW` (`TYPE_ID: 1` без `STATUS_ID = NEW` — лид, заведённый вручную
уже «в работе», отвечен в момент создания; таких единицы, но без них он считался бы
необработанным вечно).

⚠ Фильтр по `CREATED_TIME` метод понимает ТОЛЬКО в JSON-теле: form-data (`filter[>=CREATED_TIME]`)
он молча игнорирует и отдаёт всю историю — 466 479 записей. SDK шлёт JSON через axios; при любой
замене транспорта это первое, что нужно перепроверить.

### Связь лид → сделка ЕСТЬ, но у 10 % сделок

Август 2026, одним снимком 2026-09-04: **987 сделок из 10 178** имеют заполненный `LEAD_ID`
(9,7 %); успешных с лидом 640, без лида 5 536, всего успешных 6 176 — сходится по построению.

⚠ Числа «636 успешных из лидов при 6 076 по порталу» ниже по документу сняты раньше, другим

Это принципиально лучше, чем на тестовом портале (там 0), и принципиально хуже, чем нужно ТЗ.

конверсия — по сделкам с лидом, выручка — по всем. Складывать их в одну воронку нельзя, не сказав
об этом на экране.

наша опечатка.

#### Уволенные: отдельный проход `user.get`

`user.get` по умолчанию отдаёт только работающих (`ACTIVE: true`), а сделки уволенного остаются —
это тот самый случай, ради которого менеджеры перечисляются ПО СДЕЛКАМ. Уволенные читаются вторым
проходом с `ACTIVE: false`; права `user_brief` для этого хватает, поле `ACTIVE` приезжает в ответе.

⚠ Проверить это по вебхуку нельзя: у боевого вебхука заказчика нет права `user` — `user.get`
отвечает `insufficient_scope`. Приложение работает под своим правом `user_brief`, и там метод
доступен.

#### `user.get` и курсор `callList` — замер 2026-09-06

Сотрудников читает `callList` SDK. Он листает НЕ по `next`, а курсором: дописывает `'>ID'` в
**строчный** `params.filter`, ставит свой `order` и `start: -1`. Документация же `user.get`
описывает заглавный `FILTER`. Что будет, если положить условия туда, проверено на ТЕСТОВОМ портале
(`bel.bitrix24.by`, право `user` у вебхука есть):

| Запрос | Ответ |
|---|---|
| `FILTER[ACTIVE]=true&FILTER[USER_TYPE]=employee` | `ID: 1, 13` — условия применились |
| `filter[>ID]=1` | `ID: 11, 13` — **курсор работает**: `ID: 1` отфильтрован |
| `FILTER[…]` **и** `filter[>ID]=1` вместе | `ID: 11, 13` — то же, что без `FILTER`: **заглавный ключ проигнорирован целиком** |
| `filter[USER_TYPE]=employee&filter[>ID]=1` | `ID: 13` — строчный `filter` применил и условие, и курсор |

Отсюда два вывода, оба уже в коде (`userListParams`):

- условия для `callList` кладём в **строчный `filter`**, иначе они молча пропадают, и список
  приезжает вперемешку с ботами и экстранетом (`ID: 11` в замере — как раз такой);
- курсор `'>ID'` этот метод понимает. Не понимай — `callList` получал бы одну и ту же первую
  страницу без конца: не «50 сотрудников из всех», а зависший на запросах фрейм.

⚠ Числа в таблице — с тестового портала (там два штатных сотрудника), и важны здесь не они, а
ПОВЕДЕНИЕ ключей.

⚠ **`ACTIVE` работает только при JSON-транспорте.** Через form-data (`filter[ACTIVE]=false`)
значение уезжает СТРОКОЙ, портал его булевым не считает, и оба прохода возвращают одно и то же —
проверено тем же замером. SDK шлёт JSON, поэтому в приложении фильтр действует; но при любой
замене транспорта это первое, что нужно перепроверить. Замер вебхуком — только JSON-телом.

#### Длительность разговоров: почему звонки читаются СТРОКАМИ и фоном

Владелец подтвердил (2026-09-06), что сумма длительности нужна. `total` её не даёт, агрегирующего
метода в разделе телефонии нет вовсе — значит строки. Замер, на котором строится решение:

| Способ | мс на страницу | Вывод |
|---|---|---|
| 8 одиночных запросов разом | 124 | так отчёт читал в первой редакции |
| **1 пакет из 50 команд** | **24** | впятеро быстрее |
| 4 пакета по 50 разом | 11 | ещё вдвое, но уже про лимиты |

Весь август (19 015 звонков, 381 страница) пакетами по 50 — **5,7 секунды и восемь HTTP-запросов**,
все строки, ноль ошибок команд.

⛔ **Здесь была ОШИБКА ЗАМЕРА, и её стоит помнить.** Первая редакция этого раздела утверждала:
«пакет НЕ ускоряет, команды внутри него идут последовательно, ускоряет только параллельность
запросов» — и отчёт был написан на одиночных запросах по восемь разом. Перемер 2026-09-06
показал обратное: пакет ускоряет впятеро. Команды внутри пакета и правда выполняются одна за
другой, но круг по сети экономится на каждой из пятидесяти — вот этого прежний вывод и не учёл.
Замечание пришло от владельца («используй batch для выборки 50 по 50»), а не от ревью.

⛔ **Страниц 381, а не 209, и разница здесь принципиальная.** Выборка идёт БЕЗ фильтра по порогу
и коду завершения — иначе недозвоны и короткие разговоры считать было бы не из чего, а отчёт
показывает их отдельными числами. Значит читаются все 19 015 записей месяца, а не 10 404,
прошедшие правило. В первой редакции этого документа стояло 209 — число из отфильтрованной
строки таблицы выше; ошибка растиражировалась по шести файлам, пока её не поймало ревью.

Замер 2026-09-06 по факту: 40 страниц пачками по 8 — 14,8 с, то есть **370 мс на страницу**, и
весь месяц ≈ **2,4 минуты**. ⚠ Этот замер делался ОДИНОЧНЫМИ запросами и уже неактуален:
пакетами тот же месяц читается за 5,7 секунды (таблица выше). Звонки всё равно читаются
**фоном после основного
отчёта**, как справка блока 7 и история стадий в отчёте 1, а не задерживают первые числа на экране.

⚠ Больше 50 строк за вызов метод не отдаёт: `limit: 200` он молча игнорирует и возвращает те же 50.

⚠ Листать можно и смещением, и курсором `>ID` — проверено на дне с 997 звонками: 20 страниц, 997

ноль здесь — это «портал не умеет спросить», а не «таких дел нет». Показать такой блок значило бы
напечатать ноль там, где ответа не существует.

⛔ **Старые счета (`crm.invoice.list`) мертвы.** Метод отвечает без ошибки и отдаёт ноль: заказчик
перешёл на смарт-процессы, а прежний отчёт считал сущность, которой больше не пользуются. Блок
«Счета» переносить не из чего.

⚠ **`TYPE_ID: 6` — это НЕ работа человека.** 13 781 дело из 36 571 создано интеграциями:
`REST_APP` (обмен с 1С) — 12 896, `IMOPENLINES_SESSION` — 83. Прежний отчёт группировал по
`PROVIDER_ID` и честно показал бы строку «1CTOTAL» рядом со встречами менеджера. В новом отчёте
считаются ВИДЫ ДЕЛ, а не провайдеры: звонки, письма, встречи, задачи.

⚠ **Дела-звонки дублируют телефонию.** 18 418 дел `VOXIMPLANT_CALL` — это те же звонки, что
`voximplant.statistic.get` отдаёт с длительностью. В отчёте звонки берутся из телефонии (там есть
длительность и порог), а из дел — только письма, встречи и задачи, иначе одни и те же звонки

⛔ **Команда пакета — это СТРОКА ЗАПРОСА, и ключ фильтра в ней обязан быть закодирован.**
Замер сначала дал бессмыслицу — «у одного сотрудника 31 949 писем за август» при 4 338 на весь
портал. Причина: в команде `crm.activity.list?filter[>=CREATED]=2026-08-01…` знак `=` внутри
скобок разрезает ключ, и портал теряет условие ЦЕЛИКОМ, отвечая счётчиком по всему порталу без

Приложение это не задевает: `useB24Batch` передаёт команды объектами, и кодирует их SDK. Но любой
замер вебхуком и любая отладка руками — задевает, а ответ при этом выглядит правдоподобно.

**Стоимость счётчиков.** 50 команд одним пакетом — **0,38 с**. Отчёт задаёт восемь вопросов на
сотрудника (письма двумя направлениями, встречи, задачи, просрочка, лиды тремя), то есть 92
работающих сотрудника — это 736 команд, 15 пакетов, около шести секунд. Строками такое не

исходящих (`DIRECTION: 2`). Разрез тот же, что у звонков, и берётся тем же счётчиком.

⚠ Именно так, а не наоборот, и эта строка уже была написана здесь ЗАДОМ НАПЕРЁД. Числа

две обратные шкалы в одной голове не держатся. Сверяйтесь с таблицей, а не с памятью.

### Перечисление менеджеров: цепочка команд в одном пакете

Списка «кто ответственный за сделки этого направления» в REST нет, а `user.get` отдаёт только
АКТИВНЫХ сотрудников — сделки уволенных выпали бы из матрицы целиком. Поэтому распорядители
перечисляются по самим сделкам: команда просит одну сделку с наименьшим `ASSIGNED_BY_ID`, большим
предыдущего, а в пакете команды ссылаются друг на друга через `$result[...]`.

⚠ Ссылки `$result` работают и через SDK (`actions.v2.batch.make` с именованными командами) —
проверено на боевом портале. Это не документированная «фишка», а обычная подстановка Битрикс24.

| Что | Время |
|---|---|
| цепочка из 50 команд, `start: 0` | 2,8 с |
| та же цепочка, `start: -1` (без подсчёта итога) | **0,9 с** |
| цепочка по ВСЕМ сделкам направления, `start: 0` | 4,5 с |
| то же, `start: -1` | **0,6 с** |

Значения в обоих режимах СОВПАДАЮТ: `start: -1` отключает подсчёт общего числа записей, а
сортировку соблюдает. Отчёт ходит только в быстром режиме.

⚠ **Главная ловушка.** Когда разные значения кончились, команда возвращает пустой ответ, ссылка
`$result[...]` у следующей не разрешается, фильтр `>ПОЛЕ` пропадает — и цепочка НАЧИНАЕТСЯ
СНАЧАЛА. Ошибки при этом нет: портал спокойно отдаёт первое значение по второму кругу (проверено:
цепочка из 12 команд на направлении с девятью распорядителями вернула `14, 2039, …, 5577, ∅, 14,
2039`). Читать ответ можно только функцией, которая обрывается на первом пустом ответе и на
первом значении, которое не больше предыдущего, — `readDistinctChain` в `app/utils/managerQuery.ts`.

|---|---|---|
| Общее | 70 | 161 |
| Оптовые продажи | — | 85 |
| Новые продажи | 9 | 88 |
| Интернет-магазин | — | 53 |

⚠ Дело не только в скорости. Двумя компаниями клеток было бы 812 при пороге `CELL_AUTO_MAX` = 800
— отчёт ушёл бы в режим «стадии по кнопке» и показал бы одни итоги. С одной компанией он считает
стадии сразу.

## Постраничное чтение: платит отчёт за СОРТИРОВКУ, а не за круги по сети (замер 2026-09-07)

Замер по боевому порталу, август, одни и те же страницы каждым способом:

| Выборка | курсор `>ID` + `order ID ASC` | пакет + `order` | **пакет БЕЗ `order`** |
|---|---|---|---|
| успешные сделки без лида (`crm.deal.list`) | 271 мс/стр | 547 | **32** |
| лиды для истории (`crm.lead.list`) | 214 мс/стр | 38 | **17** |
| история стадий (`crm.stagehistory.list`) | 217 мс/стр | 266 | 163 |

⛔ **Пакет сам по себе не ускоряет, а местами вредит**: у `crm.deal.list` пакет С сортировкой — 547
мс/стр против 271 мс/стр курсором, то есть ВДВОЕ ХУЖЕ. Всё ускорение даёт снятие `order`.

⚠ Отсюда следствие, которое важнее самой цифры: **курсор структурно привязан к дорогой
сортировке.** Он листает по `'>ID'`, и порядок по `ID` нужен ему по устройству — отказаться от
сортировки, не отказавшись от курсора, нельзя. Поэтому «читать пакетом» и «читать без сортировки»
здесь одно решение, а не два.

⚠ **Прежняя запись обещала двадцатикратное ускорение от пакета — это была ошибка замера.** Тот
замер сравнивал курсор С сортировкой против пакета БЕЗ неё и приписал разницу пакету.

### Смещение не теряет и не дублирует — проверено на ВСЕЙ выборке

Не на первых страницах, а целиком: успешные сделки без лида за август, 9 563 записи, 192 страницы.

| Способ | Время | Строк | Дублей | Потеряно |
|---|---|---|---|---|
| курсор `>ID` (эталон) | 41 с | 9 563 | 0 | — |
| смещение пакетами, без `order` | **8 с** | 9 563 | 0 | **0** |

`total` до и после прохода совпал — данные за время чтения не менялись.

⚠ Порядок страниц без `order` портал выбирает сам, и по `ID` он НЕ идёт: у `crm.deal.list` строки
внутри страницы приходят вперемешку. Полагаться на него как на сортировку нельзя — только на то,
что за один проход он не меняется. Поэтому читающая сторона обязана сводить строки по `ID`
(`dedupeById`): за проход данные могут поехать, и тогда окно сдвинется вместе с ними.

### Что переведено, а что намеренно нет

| Выборка | Страниц (август) | Было | Стало |
|---|---|---|---|
| успешные сделки без лида | 192 | ≈ 52 с | **≈ 6 с** |
| лиды для истории | 78 | ≈ 17 с | **≈ 1,3 с** |
| история стадий | 129 | ≈ 28 с | ≈ 28 с — **не переводится** |

⚠ **История стадий оставлена на курсоре намеренно.** Выигрыш там 1,3× (метод медленный сам по
себе), а курсор устойчив к записи во время выборки, чего у смещения нет. Семь секунд не стоят
этой потери.

## Лимит интенсивности запросов (по документации платформы, 2026-09-07)

Портал считает запросы «дырявым ведром» (Leaky Bucket):

| Тариф | Восстановление | Ведро |
|---|---|---|
| Энтерпрайз | 5 запросов/с | 250 |
| Прочие | 2 запроса/с | 50 |

Превышение — код **`QUERY_LIMIT_EXCEEDED`**, HTTP **503**, текст «Превышена интенсивность
HTTP-запросов к Битрикс24». Рекомендация платформы: уменьшить частоту и **повторять с растущей
задержкой**, не пускать параллельные серии с одного адреса.

⛔ **Отказ ОДНОЙ команды делает неуспешным ВЕСЬ пакет.** Проверено по сборке SDK 2.2.0
(`processing/v2/abstract-processing.mjs`): по каждой команде создаётся `AjaxResult`, и если у неё
статус не 200 или есть ошибка, SDK кладёт ошибку во ВНЕШНИЙ результат под ключом команды
(`getErrorsByKey`). То есть `isSuccess` пакета становится ложным.

⚠ Ответы остальных сорока девяти при этом НЕ пропадают: `getData()` базового `Result` отдаёт их
независимо от успеха. Выбрасывает их НАШ код — он проверяет `isSuccess` первым и повторяет пакет
целиком. Это решение приложения, а не свойство платформы: неизвестно, каких именно строк не
хватает, а неполная страница в выручке хуже честного повтора.

⚠ Отсюда два следствия для кода:
- решение «повторять или нет» принимается по КОДУ из `getErrorsByKey()`, а не по тексту
  `getErrorMessages()`: текст портал отдаёт на своём языке и меняет между версиями;
- повторяется ПАКЕТ ЦЕЛИКОМ, а не упавшая команда: пакет — это один запрос, и ведро он занимает
  целиком; послать «недостающую» команду отдельно значит послать ещё один запрос ровно тогда,
  когда портал просит реже.

⚠ **У SDK есть СВОЙ повтор — но он про другой случай.** `AbstractHttp` крутит попытки
(`maxRetries`, по умолчанию 3), а `RestrictionManager.handleError` узнаёт `QUERY_LIMIT_EXCEEDED` и
статус 503 и ждёт с растущей паузой. Это уровень HTTP-ЗАПРОСА. Пакет с отказавшей КОМАНДОЙ
приходит со статусом 200 — ошибка лежит внутри ответа, и встроенный повтор её не видит вовсе.
Поэтому повтор в `useB24Batch` не дублирует SDK, а закрывает случай, до которого тот не достаёт.

⚠ И ещё одно, менее очевидное: у неуспешного `AjaxResult` **`getTotal()` возвращает 0**, а
`getData()` — `undefined`. Код, читающий их без проверки `isSuccess`, превратил бы отказ портала
в честный ноль на экране.
