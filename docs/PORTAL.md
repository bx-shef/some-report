# PORTAL.md — что реально есть в портале

> Last reviewed: 2026-09-02

Замер по живому REST тестового портала (`bel.bitrix24.by`, только чтение). Это НЕ предположения:
каждое утверждение ниже получено запросом. Документ отвечает на вопрос «а посчитается ли вообще
то, что просит ТЗ» — и по двум блокам ответ отрицательный.

⚠ Ключ доступа в репозиторий не попадает и попасть не должен: он живёт в переменной окружения
разработчика. В коде, тестах и CI его нет.

## Итог одной строкой

**Четыре из шести блоков ТЗ считаются на текущем портале как есть. Два — не считаются вообще:
данных, которые они требуют, в Битрикс24 нет ни поля, ни справочника.**

## Что мешает (по убыванию важности)

### 1. Причин брака лида не существует как данных

Справочник стадий лида на портале:

| Код | Имя | Семантика |
|---|---|---|
| `NEW` | Не обработан | — |
| `IN_PROCESS` | В работе | — |
| `PROCESSED` | Обработан | — |
| `CONVERTED` | Качественный лид | `S` (успех) |
| `JUNK` | Некачественный лид | `F` (провал) |

Стадия брака **одна**. Пользовательских полей у лида **ноль** (`crm.lead.fields` → ни одного
`UF_`). Отдельного системного поля «причина отказа» у лида в Битрикс24 **нет** — есть только
свободный текст `STATUS_DESCRIPTION`, по которому группировать нельзя.

Значит блок ТЗ **«Брак лидов: дубль / спам / нецелевой запрос / сервисное обращение»** сейчас
посчитать не из чего. Отчёт покажет одну строку «Некачественный лид — 100 %».

**Что нужно сделать в портале** (выбирает заказчик, работа администратора, не разработчика):

- **Вариант А — стадии.** Завести четыре пользовательские стадии лида с семантикой «провал»:
  «Дубль», «Спам», «Нецелевой запрос», «Сервисное обращение». Тогда брак = все стадии с
  семантикой `F`, а причина = сама стадия. Отчёт при этом уже готов: он читает справочник
  портала, а не зашитый список.
  *Плюс:* менеджер закрывает лид одним действием. *Минус:* стадий в воронке станет больше.
- **Вариант Б — поле-список.** Одно пользовательское поле «Причина отказа» на лиде, обязательное
  при переводе в `JUNK`. *Плюс:* воронка не разрастается. *Минус:* два действия вместо одного, и
  поле легко оставить пустым — в отчёте появится строка «Причина не указана».

Рекомендую **вариант А**: он не даёт менеджеру закрыть лид, не назвав причину.

### 2. Причин проигрыша сделки тоже не существует как данных

Стадии сделки: `NEW`, `PREPARATION`, `PREPAYMENT_INVOICE`, `EXECUTING`, `FINAL_INVOICE`,
`WON` (`S`), `LOSE` (`F`), `APOLOGY` (`F`). Пользовательских полей у сделки — **ноль**. Поля
«причина проигрыша» в Битрикс24 нет.

Значит блок ТЗ **«Разбивка причин проигрыша: цена / срок поставки / купил у другого / не можем
поставить / прочее»** сейчас посчитать не из чего.

Решение то же: либо стадии с семантикой `F` по числу причин, либо поле-список на сделке.

⚠ Заодно это подтверждает решение в коде: «проиграна» определяется **по семантике**, а не по коду
`LOSE`. Стадий провала на портале уже две (`LOSE` и `APOLOGY`), и зашитый список кодов потерял бы
половину проигранных сделок.

### 3. Сделки не связаны с лидами

Все четыре сделки портала имеют `LEAD_ID` пустым. Пока связи нет:

- «Квалифицировано в сделку» = 0, потому что квалификация определяется наличием сделки у лида;
- вся выручка попадает в «сделки без лида-родителя» и не раскладывается по источникам.

Это нормально для тестового портала, где сделки заводили руками. Но на портале заказчика нужно
проверить то же самое: если менеджеры создают сделки не конвертацией лида, а с нуля, **воронка
ТЗ не соберётся** — связывать будет нечем.

### 4. Валюты разные, и это уже реальность

`crm.currency.list` портала:

| Валюта | Базовая | Курс |
|---|---|---|
| BYN | да | 1.0000 |
| RUB | нет | 3.5300 за 100 |
| USD | нет | 2.1400 за 1 |
| EUR | нет | 2.4400 за 1 |

Сделки на портале уже в разных валютах (есть и BYN, и RUB). Складывать `OPPORTUNITY` без
приведения нельзя — сумма получится бессмысленной, но выглядеть будет как обычное число.

Хорошая новость: приводить есть чем и без справочника курсов на нашей стороне —
`сумма в базовой = OPPORTUNITY × AMOUNT / AMOUNT_CNT`. Открытый вопрос остаётся только один: курс
на **дату сделки** или **текущий**. REST отдаёт текущий; курс на дату потребовал бы хранить
историю, то есть backend.

## Что работает и как это читать

### Семантика приезжает готовой

`crm.lead.list` отдаёт `STATUS_SEMANTIC_ID` (`P` в работе / `S` успех / `F` провал), а
`crm.deal.list` — `STAGE_SEMANTIC_ID`. То есть **справочник статусов нужен только для ИМЁН**, сама
классификация приходит вместе с записью. Это заметно упрощает адаптер и убирает целый класс
ошибок.

### ⚠ Ловушка `crm.item.list`: неизвестное поле в `select` молча возвращает пустоту

Универсальный `crm.item.list` для лидов (`entityTypeId=1`) **переименовывает** поля:
`STATUS_ID` приезжает как **`stageId`**, а не `statusId`. Запрос с `select: ["statusId"]` **не
даёт ошибки** — он возвращает записи, у которых поле просто отсутствует. То есть отчёт получил бы
пустые статусы и посчитал бы всё как «в работе», не сообщив ни о чём.

Отсюда два правила для адаптера:

1. Для лидов и сделок брать **классические** `crm.lead.list` / `crm.deal.list` — там имена полей
   совпадают с документацией и со справочниками.
2. Если всё же понадобится `crm.item.list` — проверять, что запрошенные поля ДЕЙСТВИТЕЛЬНО
   пришли, а не полагаться на молчание метода.

### Права

Вебхук отдаёт скоупы `crm`, `user`, `userfieldconfig` и прочие — то есть чтения CRM хватает.
Приложению (не вебхуку) мы просим `crm`, `placement`, `user_brief`; лишнего не нужно.

## Объёмы

На тестовом портале 8 лидов и 4 сделки — по ним о производительности судить нельзя. Порядок цифр
портала заказчика надо выяснить отдельно: от него зависит, хватит ли выборки из фрейма или
понадобится backend (см. «Когда понадобится backend» в `CLAUDE.md`).

## Проверено адаптером на живых данных

Адаптер (`app/utils/b24Adapter.ts`) прогнан по этому же порталу целиком — от REST до посчитанного
отчёта. Прогон подтвердил каждое утверждение выше, а не только пересказал их:

| Что проверяли | Результат |
|---|---|
| Валюта отчёта | `BYN` — базовая валюта портала определилась верно |
| Конвертация | сделка на 456 000 RUB превратилась в **16 097 BYN** (курс 3,53 за 100, а не за 1) |
| Обе стадии провала | в разбивку попали и «Сделка провалена», и «Анализ причины провала» — зашитый `LOSE` потерял бы половину |
| Лиды «сконвертирован» без сделки | **7 из 8** — ровно тот случай, который описан в §3 |
| Сделки без лида-родителя | **4 из 4** — в разрез источников не попала ни одна |
| Сходимость | сумма лидов по источникам совпала со сводкой |
| Ни одного `NaN` | ни в долях, ни в суммах |

⚠ Строка «квалифицировано: 0» на этом портале — **не дефект отчёта**, а прямое следствие §3: связи
лид → сделка нет ни у одной сделки, а квалификация определяется именно ею. Отчёт честно
показывает ноль и отдельно сообщает, что 7 лидов помечены сконвертированными без сделки.

## Что из этого следует для ТЗ

| Блок ТЗ | Считается сейчас | Что нужно |
|---|---|---|
| Сводка (KPI) | да, кроме «квалифицировано» | связывать сделки с лидами |
| Воронка | нет | связывать сделки с лидами |
| Обработка лидов | частично | источник «первого ответа» — дела (`crm.activity.list`), нужен отдельный замер |
| **Брак по причинам** | **нет** | стадии или поле-список в портале |
| Потери до сделки | да | — |
| **Причины проигрыша** | **нет** | стадии или поле-список в портале |
| Эффективность источников | да, кроме продаж | связывать сделки с лидами |
