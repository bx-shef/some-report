# DEPLOY.md — сборка и выкат

> Last reviewed: 2026-09-02

Отчёт — статический сайт. Backend'а нет, базы нет, состояния на сервере нет: nginx раздаёт файлы,
всё остальное происходит в браузере внутри фрейма портала.

Схема повторяет `client-bank-alfa-by`, чтобы не заводить второй способ выкатывать одно и то же:

```
git push в main ──▶ CI (lint, типы, тесты, сборка)
                      │ зелёный
                      ▼
                 docker build ──▶ GHCR (ghcr.io/bx-shef/some-report:latest)
                                     │
                                     ▼
                              Watchtower на сервере
                                     │
                                     ▼
                       nginx-проект за общим nginx-proxy (TLS — Let's Encrypt)
```

## Что нужно настроить один раз

### 1. Переменная репозитория `NUXT_PUBLIC_SITE_URL`

**Settings → Secrets and variables → Actions → Variables** (именно Variables, не Secrets: адрес
публичный).

Значение — адрес, с которого раздаётся приложение, например `https://report.bx-shef.by`.

⚠ Это **build-time** значение: SSG запекает его в статику. Поменять его на работающем сервере
нельзя — нужна пересборка (`workflow_dispatch` на `main` как раз для этого).

⚠ Без него выкат **падает намеренно** (шаг «Проверить, что публичный адрес задан»). Причина: из
этого адреса страница установки строит абсолютный URL обработчика плейсмента, а относительный
`placement.bind` не примет. Собранный без адреса образ выглядел бы рабочим и молча не
устанавливался бы в портал.

### 2. DNS и TLS

`A`-запись на сервер, дальше общий `nginx-proxy` + `acme-companion` выпишут сертификат по
`VIRTUAL_HOST`/`LETSENCRYPT_HOST` (как у соседних проектов).

### 3. Watchtower

Следит за `ghcr.io/bx-shef/some-report:latest` и подменяет контейнер после публикации нового
образа. Отдельной настройки под этот проект не требует, если он уже поднят на сервере.

## Что делает сборка

`Dockerfile`, стадия `builder`:

1. `pnpm install --frozen-lockfile --ignore-scripts` — ровно то, что в коммите;
2. `pnpm generate` — статика в `.output/public`;
3. **гарды на артефакте** — есть ли `/app`, `/install` и `404.html`. Тесты проверяют исходники,
   гарды — то, что реально уехало в образ; между ними и живут молчаливые дефекты выката;
4. `scripts/cspHashes.ts` — подставляет sha256-хеши инлайновых скриптов в `nginx.conf`;
5. проверка, что плейсхолдер `__CSP_SCRIPT_HASHES__` исчез и хеши на месте.

Стадия `runner` — `nginxinc/nginx-unprivileged` (работает не от root, слушает 8080), внутрь
кладётся только статика и конфиг. `nginx -t` гоняется на СБОРКЕ: синтаксическая ошибка роняет
образ здесь, а не всплывает при выкате.

## Про CSP: почему хеши, а не `'unsafe-inline'`

Nuxt печатает в HTML инлайновый `<script>` с `window.__NUXT__.config`. Разрешить его можно двумя
способами:

- `script-src 'unsafe-inline'` — снимает защиту от XSS **целиком**: браузер перестаёт отличать наш
  скрипт от вставленного через дыру;
- перечислить sha256-хеш этого скрипта.

Берём второе. Считать хеш надо по **собранному** HTML: внутри `window.__NUXT__.config` лежит в том
числе `siteUrl`, то есть текст скрипта зависит от аргументов сборки, и заранее посчитанный хеш не
совпал бы.

⚠ Если плейсхолдер останется незаменённым, браузер увидит в `script-src` мусорный токен,
заблокирует собственный бандл приложения и покажет белый экран. **В логе сервера при этом не будет
ни строчки** — CSP нарушает клиент. Поэтому проверка стоит гардом в `Dockerfile`, а не в
человеческой внимательности.

## Про `frame-ancestors`: без него приложение либо не работает, либо небезопасно

Два требования тянут в разные стороны, и удовлетворяет оба только `frame-ancestors`:

- **разрешить** порталам Битрикс24 встраивать нас — иначе на месте виджета пустая область без
  единой ошибки в интерфейсе;
- **запретить** всем остальным — иначе нашу страницу можно встроить в любой чужой сайт.

`X-Frame-Options` мы **не ставим**: он не умеет списка доменов, а в части браузеров перебивает CSP
и возвращает пустую область.

⚠ Список зон в `nginx.conf` — облачные домены Битрикс24. **Коробочный портал на своём домене
должен быть добавлен туда явно**, иначе получит пустой фрейм. Это первое, что нужно проверять при
жалобе «приложение не открывается».

## Проверка после выката

```bash
# 1. Статика раздаётся
curl -sI https://<адрес>/ | head -1                    # 200

# 2. Служебные страницы попали в сборку
curl -sI https://<адрес>/app/ | head -1                # 200
curl -sI https://<адрес>/install/ | head -1            # 200

# 3. POST на обработчик плейсмента не даёт 405 (портал открывает его POST-запросом)
curl -sI -X POST https://<адрес>/app/ | head -1        # 200

# 4. CSP на месте и без unsafe-inline в script-src
curl -sI https://<адрес>/ | grep -i content-security-policy

# 5. Фрейм разрешён порталам Битрикс24
curl -sI https://<адрес>/ | grep -io 'frame-ancestors[^;]*'
```

Дальше — установка на портал: открыть `https://<адрес>/install` из портала и убедиться, что пункт
появился в **CRM-аналитика → Приложения**. Порядок и типовые ошибки — [`EMBEDDING.md`](EMBEDDING.md).

## Локальная проверка образа

```bash
docker build --target runner \
  --build-arg NUXT_PUBLIC_SITE_URL=https://report.example.com \
  --build-arg NUXT_PUBLIC_COMMIT_SHA=local \
  -t some-report:local .

docker run --rm -p 8080:8080 some-report:local
# http://localhost:8080/app?preview=1
```

⚠ `?preview=1` — штатный обход заглушки «работает только внутри Битрикс24». Без него страница
приложения покажет объяснение, и это правильно.

## Откат

Образы тегируются и как `latest`, и как `sha-<коммит>`. Откат — переключить контейнер на
предыдущий `sha-…` (Watchtower следит за `latest`, поэтому на время отката его для этого
контейнера нужно отключить, иначе он вернёт `latest` обратно).
