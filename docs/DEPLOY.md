# DEPLOY.md — сборка и выкат

> Last reviewed: 2026-09-04

Отчёт — статический сайт. Backend'а нет, базы нет, состояния на сервере нет: nginx раздаёт файлы,
всё остальное происходит в браузере внутри фрейма портала.

Схема повторяет `client-bank-alfa-by`, чтобы не заводить второй способ выкатывать одно и то же:

```
git push в main ──▶ CI (lint, типы, тесты, сборка)
                      │ зелёный
                      ▼
                 docker build ──▶ GHCR (ghcr.io/bx-shef/some-report:latest)
                                     │
                                     ▼
                              Watchtower на сервере
                                     │
                                     ▼
                       nginx-проект за общим nginx-proxy (TLS — Let's Encrypt)
```

## Что нужно настроить один раз

### 1. Переменная репозитория `NUXT_PUBLIC_SITE_URL`

**Settings → Secrets and variables → Actions → Variables** (именно Variables, не Secrets: адрес
публичный).

Значение — адрес, с которого раздаётся приложение: `https://some-report.bx-shef.by`.

⚠ Он обязан совпадать с `DOMAIN` в [`deploy/.env.example`](../deploy/.env.example). Раньше здесь
стоял пример с другим адресом, и выполнение инструкции буквально воспроизводило ровно то
расхождение, от которого она же и предостерегает ниже.

⚠ Это **build-time** значение: SSG запекает его в статику. Поменять его на работающем сервере
нельзя — нужна пересборка (`workflow_dispatch` на `main` как раз для этого).

⚠ Без него выкат **падает намеренно** (шаг «Проверить, что публичный адрес задан»). Причина: из
этого адреса страница установки строит абсолютный URL обработчика плейсмента, а относительный
`placement.bind` не примет. Собранный без адреса образ выглядел бы рабочим и молча не
устанавливался бы в портал.

### 2. DNS и TLS

`A`-запись на сервер, дальше общий `nginx-proxy` + `acme-companion` выпишут сертификат по
`VIRTUAL_HOST`/`LETSENCRYPT_HOST` (как у соседних проектов).

### 3. Первый запуск контейнера на сервере

**Что должно быть на сервере ДО этого шага** (общая инфраструктура, одна на все проекты):

```bash
docker network ls | grep proxy-net          # сеть должна существовать
docker ps --format '{{.Names}}' | grep -E 'nginx-proxy|acme|watchtower'
```

- сеть `proxy-net`;
- `nginx-proxy` + `acme-companion` — маршрутизация по домену и сертификаты;
- Watchtower с `--label-enable` — только для будущих обновлений.

⚠ Без сети `proxy-net` шаг ниже падает с `network proxy-net declared as external, could not be
found`. Если её нет — инфраструктуру поднимают отдельно, это не часть этого проекта.


⚠ **Это отдельный шаг, и его легко пропустить.** Watchtower только ОБНОВЛЯЕТ уже существующие
контейнеры — создавать новые он не умеет. Пока контейнер не поднят руками хотя бы раз,
`nginx-proxy` отдаёт на домен **503 Service Temporarily Unavailable**: маршрута к upstream у него
нет. Со стороны это выглядит как «выкат не сработал», хотя образ в GHCR лежит и он исправен.

```bash
# на сервере
mkdir -p /home/bitrix/some-report && cd /home/bitrix/some-report

# Забрать файлы из репозитория. Он публичный, поэтому без авторизации.
BASE=https://raw.githubusercontent.com/bx-shef/some-report/main/deploy
curl -fsSLO "$BASE/docker-compose.prod.yml"
curl -fsSL  "$BASE/.env.example" -o .env.example

cp .env.example .env && nano .env      # DOMAIN, LETSENCRYPT_EMAIL

docker compose -f docker-compose.prod.yml pull
docker compose -f docker-compose.prod.yml up -d
docker compose -f docker-compose.prod.yml ps   # снимок состояния
```

⚠ `docker compose ps` НЕ ждёт — это разовый снимок. При `start_period: 10s` сразу после `up -d`
он честно покажет `starting`. Подождите секунд пятнадцать и повторите, либо смотрите непрерывно:
`watch docker compose -f docker-compose.prod.yml ps`.

⚠ `curl -f` здесь не для красоты: без него сервер молча запишет в файл HTML-страницу ошибки
GitHub, а `docker compose` потом отругается на невалидный YAML — и искать будут поломку compose,
а не то, что файл не скачался.

⚠ `.env.example` качается с явным `-o`: у `curl -O` имя берётся из URL, а файл начинается с точки —
в каталоге он окажется скрытым, и `ls` покажет пустоту там, где всё на месте.

⚠ `DOMAIN` в `.env` обязан совпадать с `NUXT_PUBLIC_SITE_URL`, с которым собран образ. Разойдутся —
страница установки построит адрес обработчика плейсмента на ЧУЖОЙ домен, и портал откроет пустоту.

Сертификат `acme-companion` выпишет сам через десяток-другой секунд после старта. Пока его нет,
HTTPS отвечает ошибкой TLS вида `unrecognized name` — это нормально ровно до первого выпуска.

### 4. Watchtower — только для последующих обновлений

Следит за `ghcr.io/bx-shef/some-report:latest` и подменяет контейнер после публикации нового
образа. Отдельной настройки под этот проект не требует, если он уже поднят на сервере с
`--label-enable`: метку `com.centurylinklabs.watchtower.enable=true` контейнер несёт сам.

## Что делает сборка

`Dockerfile`, стадия `builder`:

1. `pnpm install --frozen-lockfile --ignore-scripts` — ровно то, что в коммите;
2. `pnpm generate` — статика в `.output/public`;
3. **гарды на артефакте** — есть ли `/app`, `/install` и `404.html`. Тесты проверяют исходники,
   гарды — то, что реально уехало в образ; между ними и живут молчаливые дефекты выката;
4. `scripts/cspHashes.ts` — подставляет sha256-хеши инлайновых скриптов в `nginx.conf`;
5. проверка, что плейсхолдер `__CSP_SCRIPT_HASHES__` исчез и хеши на месте.

Стадия `runner` — `nginxinc/nginx-unprivileged` (работает не от root, слушает 8080), внутрь
кладётся только статика и конфиг. `nginx -t` гоняется на СБОРКЕ: синтаксическая ошибка роняет
образ здесь, а не всплывает при выкате.

## Про CSP: почему хеши, а не `'unsafe-inline'`

Nuxt печатает в HTML инлайновый `<script>` с `window.__NUXT__.config`. Разрешить его можно двумя
способами:

- `script-src 'unsafe-inline'` — снимает защиту от XSS **целиком**: браузер перестаёт отличать наш
  скрипт от вставленного через дыру;
- перечислить sha256-хеш этого скрипта.

Берём второе. Считать хеш надо по **собранному** HTML: внутри `window.__NUXT__.config` лежит в том
числе `siteUrl`, то есть текст скрипта зависит от аргументов сборки, и заранее посчитанный хеш не
совпал бы.

⚠ Если плейсхолдер останется незаменённым, браузер увидит в `script-src` мусорный токен,
заблокирует собственный бандл приложения и покажет белый экран. **В логе сервера при этом не будет
ни строчки** — CSP нарушает клиент. Поэтому проверка стоит гардом в `Dockerfile`, а не в
человеческой внимательности.

## Про `frame-ancestors`: без него приложение либо не работает, либо небезопасно

Два требования тянут в разные стороны, и удовлетворяет оба только `frame-ancestors`:

- **разрешить** порталам Битрикс24 встраивать нас — иначе на месте виджета пустая область без
  единой ошибки в интерфейсе;
- **запретить** всем остальным — иначе нашу страницу можно встроить в любой чужой сайт.

`X-Frame-Options` мы **не ставим**: он не умеет списка доменов, а в части браузеров перебивает CSP
и возвращает пустую область.

⚠ Список origin'ов живёт в `Dockerfile` (`ENV B24_PORTAL_ORIGINS`) и подставляется в `nginx.conf`
при старте контейнера. Облачные зоны Битрикс24 покрыты wildcard'ами; **коробочный портал на своём
домене нужно добавить в этот список** — см. следующий раздел. Это первое, что нужно проверять при жалобе
«приложение не открывается».

## Коробочный портал на своём домене

Приложение хостится **одним экземпляром на всех клиентов**, поэтому список порталов, которым
разрешено его встраивать, — часть продукта, а не настройка сервера. Он живёт в `Dockerfile`
(`ENV B24_PORTAL_ORIGINS`) и приезжает вместе с образом. **На сервере при подключении клиента
ничего прописывать не нужно.**

Облачные порталы (`*.bitrix24.by`, `.ru`, `.com`, …) покрыты wildcard'ами по зонам — новый
облачный клиент подключается без единой правки.

Отдельной строки требует только **коробочный** портал: он живёт на своём домене и ни под один
wildcard не подходит. Подключая такого клиента:

1. добавить его origin в `ENV B24_PORTAL_ORIGINS` в `Dockerfile` — через пробел, с `https://`,
   без слеша на конце:

   ```dockerfile
   ENV B24_PORTAL_ORIGINS="https://*.bitrix24.ru … https://bitrix24.tech https://bitrix.ankron.by https://портал.клиента"
   ```

2. смержить — образ соберётся и выкатится штатно. Значение проверяется при сборке и при каждом
   старте контейнера (`deploy/validate-portal-origins.sh`): опечатка вида `http://` или лишний
   символ ронят сборку, а не отдают испорченный заголовок.

⚠ Забыть про это дорого: портал покажет на месте отчёта **пустую область** — без единой ошибки в
интерфейсе и без строки в логах nginx. Заголовок присылает наш сервер, нарушение фиксирует
браузер, и увидеть его можно только в консоли разработчика внутри фрейма.

Проверка, что домен клиента действительно в заголовке:

```bash
curl -sI https://<адрес>/ | grep -io 'frame-ancestors[^;]*'
# в выводе обязан быть домен портала клиента
```

Переменную окружения `B24_PORTAL_ORIGINS` можно переопределить — это запасной ход для клиента,
который поднимает **свою** копию приложения на своём сервере. В нашем выкате она не задаётся.

## Заголовки: кто какой ставит

Приложение и `nginx-proxy` — два сервера в одной цепочке, и заголовки между ними поделены:

| Заголовок | Кто ставит | Почему так |
|---|---|---|
| `Content-Security-Policy` | приложение | знает свои скрипты и их хеши |
| `Cache-Control`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` | приложение | про его собственную статику |
| **`Strict-Transport-Security`** | **`nginx-proxy`** | его ставит тот, кто терминирует TLS |

⚠ `Permissions-Policy` приложение ставит и на документы, и на ассеты `/_nuxt/` — набор заголовков
в этой локации свой, потому что nginx не наследует серверные `add_header` туда, где объявлен хоть
один свой.

⚠ HSTS мы намеренно **не** ставим. Контейнер не видит HTTPS вообще: снаружи к нему приходит
обычный HTTP на 8080, и знать, шифруется ли соединение до браузера, он не может. Объявлять от его
имени «только HTTPS на год вперёд» — значит утверждать то, что ему неизвестно: поднимите тот же
образ без TLS на стенде, и заголовок запрёт домен в HTTPS у всех, кто туда зайдёт.

На первом выкате заголовок приходил ДВАЖДЫ — наш и от `nginx-proxy`. Опасен дубль не был:
RFC 6797 §8.1 объявляет STS singleton-полем, браузер берёт первый и игнорирует остальные, а первым
шёл наш — то есть в силе была наша, более строгая политика.

⚠ **Цена решения:** вместе с нашим заголовком ушёл `includeSubDomains`, которого у прокси нет.
Поддоменов у этого адреса нет, так что сейчас директива не покрывала ничего; вернуть её — это одна
настройка `HSTS` у `nginx-proxy`, то есть у того, кому заголовок и принадлежит.

⚠ Из этого следует требование к серверу: **`nginx-proxy` обязан ставить HSTS сам.** Если его
отключить, сайт останется без HSTS вовсе.

## Диагностика: что означает ответ домена

| Ответ | Что это значит | Что делать |
|---|---|---|
| **503** от nginx | `nginx-proxy` жив, но за этим доменом нет контейнера | поднять контейнер (шаг 3) |
| TLS `unrecognized name` | сертификат ещё не выписан | подождать после старта контейнера; если не появился — проверить `LETSENCRYPT_HOST` |
| **502** | контейнер есть, но не отвечает | `docker compose logs app`, проверить healthcheck |
| **404** на `/app/` | статика раздаётся, но страницы нет в сборке | пересобрать; гарды в `Dockerfile` такое обязаны ловить |
| **405** на POST `/app/` | не сработал `error_page 405 =200` | сверить `nginx.conf` в образе |
| Пустая область в портале | фрейм запрещён заголовками | проверить `frame-ancestors`, добавить домен портала |

## Проверка CSP браузером — в CI

`pnpm smoke` (шаг «CSP smoke (browser)» в `ci`): после сборки скрипт `scripts/cspSmoke.ts` считает
хеши в памяти, поднимает статику с ИТОГОВЫМ заголовком и открывает `/`, `/app/?preview=1`,
`/install/` настоящим Chrome. Провал — любое нарушение CSP в консоли, ошибка страницы, не
стартовавший Nuxt или отсутствие текста, который рисует только JavaScript. Список страниц обязан
покрывать `PRERENDER_ROUTES` — иначе смоук и тест падают.

Что смоук покрывает: `script-src`, `style-src`, `img-src`, `font-src`, `default-src` — всё, что
срабатывает на одиночной странице. Что НЕ покрывает: `frame-ancestors` и `connect-src` к REST
портала. Страница открывается вне фрейма, а `?preview=1` рисует демо-набор без единого запроса
к REST, поэтому пустой фрейм из-за неверного домена в `B24_PORTAL_ORIGINS` смоук не увидит — это
по-прежнему ручная проверка в портале после выката (раздел ниже).

⚠ Зачем, если хеши подставляются и проверяются на сборке. Оба шага зовут один разбор HTML, и
ошибка в нём проходит через оба зелёной: так в прод уехала заблокированная импорт-карта — хеши на
месте, проверка на месте, приложение не стартует. Единственная проверка, которая не может соврать,
— браузер. Локально: `pnpm generate && pnpm smoke` (нужен Chrome; свой браузер — через
`CSP_SMOKE_BROWSER=/путь/к/chromium`).

Если шаг покраснел на всех ветках без изменений кода — обновился Chrome образа раннера, а
`playwright-core` в lock-файле остался прежним; лечится бампом `playwright-core`. Если в логе
«browserType.launch: Executable doesn't exist» — раннер сменил образ и Chrome в нём нет; временно
задать `CSP_SMOKE_BROWSER` после `pnpm exec playwright install chromium`. Упал с «нет текста
«…»» — сменили текст в компоненте, а маркер в `PAGES` не обновили; это не поломка CSP.

## Проверка после выката

```bash
# 1. Статика раздаётся
curl -sI https://<адрес>/ | head -1                    # 200

# 2. Служебные страницы попали в сборку
curl -sI https://<адрес>/app/ | head -1                # 200
curl -sI https://<адрес>/install/ | head -1            # 200

# 3. POST на обработчик плейсмента не даёт 405 (портал открывает его POST-запросом)
curl -sI -X POST https://<адрес>/app/ | head -1        # 200

# 4. CSP на месте и без unsafe-inline в script-src
curl -sI https://<адрес>/ | grep -i content-security-policy

# 4a. HSTS ставит nginx-proxy, а не мы — значит его отсутствие надо ЗАМЕТИТЬ.
#     Пусто здесь = сайт без HSTS вовсе; чинится настройкой прокси, не приложения.
curl -sI https://<адрес>/ | grep -i strict-transport-security

# 5. Фрейм разрешён порталам Битрикс24
curl -sI https://<адрес>/ | grep -io 'frame-ancestors[^;]*'
```

Дальше — установка на портал: открыть `https://<адрес>/install` из портала и убедиться, что пункт
появился в **CRM-аналитика → Приложения**. Порядок и типовые ошибки — [`EMBEDDING.md`](EMBEDDING.md).

## Локальная проверка образа

```bash
docker build --target runner \
  --build-arg NUXT_PUBLIC_SITE_URL=https://report.example.com \
  --build-arg NUXT_PUBLIC_COMMIT_SHA=local \
  -t some-report:local .

docker run --rm -p 8080:8080 some-report:local
# http://localhost:8080/app?preview=1
```

⚠ `?preview=1` — штатный обход заглушки «работает только внутри Битрикс24». Без него страница
приложения покажет объяснение, и это правильно.

## Откат

Образы тегируются и как `latest`, и как `sha-<коммит>`. Откат — переключить контейнер на
предыдущий `sha-…` (Watchtower следит за `latest`, поэтому на время отката его для этого
контейнера нужно отключить, иначе он вернёт `latest` обратно).
